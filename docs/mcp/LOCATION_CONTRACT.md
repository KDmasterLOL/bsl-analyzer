# Location contract v1: одно место и один конверт на все инструменты

До этого контракта каждый инструмент писал «где» по-своему: `search` — 1-based строки
без колонок, `diagnostics` — 0-based диапазон с колонками, но без пути и корня в самой
находке, `symbol_info` — одну строку 1-based при 0-based входе того же инструмента,
`graph` — вообще ничего. Потребитель обязан был знать, с кем разговаривает, прежде чем
прочесть ответ.

Теперь место и свежесть описываются одинаково везде, и сериализует их один модуль:
`crates/mcp-server/src/tools/location.rs`. Инструмент собирает типизированное значение
и отдаёт его туда; ключи он не пишет.

## Объект места

```jsonc
{
  "root_id": "",                        // обязателен; "" = основная конфигурация
  "path": "CommonModules/Продажи/Ext/Module.bsl", // относительный к root_id, разделитель "/"
  "range": {                            // опционально
    "start_line": 119, "start_character": 10,
    "end_line": 119,  "end_character": 22
  },
  "enclosing_range": { "…": "…" },      // опционально
  "position_encoding": "utf-16",        // обязателен, константа
  "module": { "kind": "ОбщийМодуль", "name": "Продажи" }, // опционально
  "schema_version": "1"                 // версия ПЛИТЫ, не инструмента
}
```

- **0-based, конец исключающий** — как в LSP и SCIP.
- **Колонки — кодовые единицы UTF-16**, и это объявлено полем, а не подразумевается.
  Единица важна: у одного и того же места есть три разные «колонки» — байтовая,
  в кодовых точках и в кодовых единицах, — и они расходятся на символах вне BMP.
- **Пара `(root_id, path)` — ключ файла.** Расширение повторяет структуру каталогов
  конфигурации, поэтому один относительный путь живёт в нескольких корнях. Пустая строка
  — зарезервированный идентификатор конфигурации.
- **Два диапазона.** `range` — имя символа; `enclosing_range` — весь узел. У находки
  диагностики имени нет, поэтому там `range` — спан самой находки, а `enclosing_range` —
  метод, который её держит.
- **Диапазоны опциональны.** Локация без них означает «файл»: так отвечают хит поиска из
  общего baseline, карточка модуля и всё, у чего позиции в источнике нет. Ноли вместо
  отсутствия были бы неправдой.

### Когда места нет

Вместо `location` приходит `location_unavailable` — машинный код, а не молчание:

| Код | Когда |
|---|---|
| `no_source_location` | у сущности нет файла по построению: объект метаданных, форма, реквизит |
| `roots_unavailable` | у ответившего снимка не было таблицы корней (загрузка опубликовала кэш графа раньше, чем загрузился проект) |
| `path_outside_registered_roots` | путь не принадлежит ни одному зарегистрированному корню |
| `absolute_path_without_pair` | у источника абсолютный путь там, где ожидалась пара: файл назван, но не как `(root_id, path)` |
| `relative_path_without_root` | известен только относительный путь, и поставить его в корень нечем. Зеркало предыдущего кода, и потому код отдельный: одно имя на два противоположных факта не даёт потребителю сказать, что именно случилось |
| `source_path_unavailable` | файл у сущности ЕСТЬ, но назвать его путь нельзя: запись VFS не выражается строкой либо отсутствует в наборе файлов корня. Отличается от `roots_unavailable`: таблица корней была на месте, не было пути |

У сущности, у которой место есть по построению, ровно один из двух ключей присутствует
всегда.

### Откуда берётся `root_id`

Две ветви, и это не деталь реализации, а обещание:

- **Корень выводится из пути** (`symbol_info`, `diagnostics`, `graph`): на входе только
  путь, пара строится по таблице корней. Файл вне всех корней локации не получает.
- **Корень приходит от источника** (`search`): он уже лежит в хите и копируется как есть,
  без проверки на регистрацию. Хит из общего baseline несёт корень чужого воркспейса —
  подменить его пустой строкой значило бы соврать, а отбросить локацию — потерять адрес,
  который источник знает, а мы нет. Такая локация в этом воркспейсе обратно не
  разрешается: `diagnostics file` по ней ответит `unknown_root`, и это честный отказ.

## Конверт

```jsonc
"freshness": {
  "source": "resident" | "graph" | "search-index",
  "revision": 42,                          // null, когда у источника нет своей идентичности
  "topology_fingerprint": "0a1b2c3d4e5f6071", // 16 hex-знаков; null, когда неизвестен
  "stale": false,
  "completeness": {
    "status": "complete" | "partial",
    "reasons": [ { "code": "output_budget", "detail": "…" } ]
  }
}
```

- **Отпечаток топологии — строка**, а не число: значение 64-битное, и JSON-число у
  JS-потребителя молча теряет точность выше 2⁵³.
- **`revision`/`topology_fingerprint`/`stale` бывают `null`.** У поиска нет собственной
  ревизии; проставить ему ревизию резидента или графа значило бы выдать чужую свежесть за
  свою — ровно то, против чего заводится контракт. Поле `source` называет, кто отвечал.
- **Полнота собирается там, где факт известен** — из возврата функции обрезки, флага
  предела, счётчика непрочитанных, — и никогда не восстанавливается разбором уже
  собранного JSON.

### Словарь причин неполноты

Закрытый: новый код — это новая версия плиты, а не новая строка на месте.

| Код | Что означает |
|---|---|
| `output_budget` | ответ обрезан бюджетом вывода; поднимите `max_output_tokens` |
| `result_cap` | сработал счётный предел (`max_findings`, `max_nodes`, предел кандидатов) |
| `index_building` | нужный части ответа индекс ещё строится |
| `unreadable_files` | какие-то файлы прочитать не удалось |
| `out_of_analysis_scope` | часть запроса вне настроенной области анализа |
| `modality_degraded` | подсистема, которой ответ обычно пользуется, была недоступна |

## Старые поля

Ничего не удалено и не переименовано. Новые ключи добавлены рядом, старые помечены
устаревшими и будут жить до следующей мажорной версии схемы своего инструмента.

| Инструмент | Устаревшее | Взамен |
|---|---|---|
| `search` | `line_start` / `line_end` (1-based, конец включающий) | `location.enclosing_range` |
| `diagnostics` | `range` (0-based, колонки в кодовых ТОЧКАХ) | `location.range` |
| `diagnostics`, `graph` | `revision`, `stale` в корне конверта | `freshness.revision`, `freshness.stale` |
| `symbol_info` | `definition` (одна 1-based строка, без корня) | `definitions[].location` |

Значения устаревших полей не изменились ни на единицу: тесты утверждают старое и новое
рядом, на одном ответе.

## Версии

Три независимые оси, и путать их не нужно:

- `contract_version` (`bsl-analyzer contract`) — что сборка ПРИНИМАЕТ: инструменты,
  действия, параметры;
- `schema_version` ответа инструмента (`search` `"3"`, `diagnostics` `"12"`,
  `graph` `"30"`) — форма ответа этого инструмента;
- `schema_version` внутри объекта места — версия самой плиты, общая для всех инструментов.

Плита versionируется отдельно именно потому, что путешествует между инструментами: её
нельзя версионировать номером одного из них.

## Что этот этап не закрывает

- Профиль `reference` (`search action=find_docs|search_docs`) остаётся как был: его хиты
  указывают в HTML-файлы справки платформы, у которых нет ни корня, ни BSL-узлов.
- У header-чанка поиска диапазонов нет: его конец строки считается другим правилом, чем у
  чанка метода, и выдавать его как исключающий конец было бы числом, которого контракт не
  имеет в виду.
- `search` не выставляет `result_cap`: усечение по `limit` происходит внутри слияния
  модальностей, и до сериализации доезжает уже урезанный список. Вывести причину из
  равенства «показано = запрошено» значило бы гадать.
