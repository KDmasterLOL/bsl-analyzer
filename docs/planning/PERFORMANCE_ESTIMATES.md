## Сравнение производительности

### Сценарий 1: SonarQube Scan (Full Analysis)

| Операция | BSL-LS (Java) | BSL Analyzer (Rust) | Улучшение |
|----------|---------------|---------------------|-----------|
| **Парсинг** | ~500 минут (8ч) | 18 сек (single) / 2 сек (8 cores) | **250x** |
| **Semantic Analysis** | ~200 минут | 35 сек (single) / 4 сек (8 cores) | **340x** |
| **Diagnostics (181)** | ~100 минут | 60 сек (single) / 8 сек (8 cores) | **100x** |
| **TOTAL** | **~800 минут (13ч)** | **~2-5 минут** | **160x-240x** |
| **Память** | ~80 GB ❌ (невозможно) | ~1-2 GB ✅ | **40x-80x меньше** |

**Примечания:**
- Java оценка экстраполирована из ERP 2.5 (~500 MB → 60 минут)
- Rust оценка основана на текущей скорости парсера (225 MB/s)
- Параллелизм: 8 ядер (через Rayon)

### Сценарий 2: LSP Incremental Update (типичная работа)

**Пользователь редактирует 1 файл:**

| Аспект | БЕЗ Salsa (Java) | С Salsa (Rust) | Улучшение |
|--------|------------------|----------------|-----------|
| **Изменение комментария** | 500-5000 ms | 20-30 ms | **25x-250x** |
| **Изменение реализации (интерфейс тот же)** | 500-5000 ms | 30-50 ms | **16x-166x** |
| **Изменение интерфейса** | 2000-10000 ms | 100-200 ms | **20x-100x** |
| **Пересчет зависимых файлов** | Все (~500-1000) | Только измененные (~5-50) | **10x-200x меньше** |

**Почему Salsa быстрее:**

1. **Кеширование результатов**
   - Salsa кеширует результаты парсинга, анализа, диагностик
   - Повторные запросы: O(1) вместо O(N)

2. **Умная инвалидация**
   - Проверяет: изменился ли интерфейс?
   - Если НЕТ → не пересчитывает зависимые модули

3. **Durability**
   - Метаданные: `Durability::HIGH` (проверяются реже)
   - Исходный код: `Durability::LOW` (проверяются чаще)

### Сценарий 3: LSP Cold Start (открытие проекта)

| Операция | BSL-LS (Java) | BSL Analyzer (Rust) | Улучшение |
|----------|---------------|---------------------|-----------|
| **Загрузка метаданных** | ~10-30 сек | ~1 сек | **10x-30x** |
| **Индексация VFS** | ~5-10 сек | ~2-3 сек | **2x-3x** |
| **Парсинг всех файлов** | ~5-10 минут | **Не требуется** (lazy) | **∞** |
| **TOTAL** | **~5-10 минут** | **~3-5 секунд** | **60x-200x** |

**Salsa + Lazy Loading:**
- Метаданные загружаются сразу (нужны для диагностик)
- Парсинг файлов — **on-demand** (только открытые)
- Semantic analysis — **on-demand** (только при необходимости)

## Потребление памяти

### Java версия (bsl-language-server)

**ERP 2.5 (~500 MB исходников):**
```
Heap memory: ~10 GB
GC overhead: ~20-30% CPU
Memory model: Все в памяти (нет LRU)
```

**Экстраполяция на 4 GB:**
```
10 GB * (4000 / 500) = 80 GB ❌
Невозможно на большинстве машин!
```

### Rust версия (bsl-analyzer с Salsa)

**Breakdown для 4GB проекта:**

| Компонент | Размер | Пояснение |
|-----------|--------|-----------|
| **VFS (FileId → path mapping)** | ~50 MB | PathInterner (80K files) |
| **File contents cache** | ~200 MB | Только измененные файлы |
| **Parse results (LRU = 128)** | ~64 MB | 128 * 500 KB |
| **Метаданные (Configuration)** | ~100 MB | Arc-shared, loaded once |
| **Symbol tables** | ~300 MB | Name → Definition mapping |
| **HIR cache (LRU = 256)** | ~128 MB | 256 * 500 KB |
| **Diagnostics cache** | ~50 MB | Recent results |
| **Indexing data** | ~200 MB | Cross-references, imports |
| **Overhead (Salsa, etc.)** | ~100 MB | Internal structures |
| **TOTAL** | **~1.2 GB** | ✅ Укладываемся в цель < 2.5 GB |

**Ключевые оптимизации:**

1. **LRU кеши** — не держим все файлы, только последние N
2. **Arc<T>** — метаданные shared между queries
3. **Salsa durability** — метаданные проверяются реже
4. **Lazy loading** — парсим только нужные файлы

## Критические факторы для больших проектов

### 1. I/O Performance

**Проблема:**
```
Чтение 4GB с диска:
  HDD (100 MB/s):  40 секунд
  SSD (500 MB/s):  8 секунд
  NVMe (3000 MB/s): 1.3 секунды
```

**Решение:**
- Salsa кеширует file contents
- VFS отслеживает изменения (не перечитывает неизменные файлы)
- Incremental: читаем только измененные файлы

### 2. Параллелизм (Rayon)

**Важно:**
- Парсинг легко параллелится (независимые файлы)
- Semantic analysis сложнее (есть зависимости)
- Используем Rayon для автоматического распараллеливания

**Пример:**
```rust
use rayon::prelude::*;

files.par_iter()
    .map(|file_id| db.parse(*file_id))  // Salsa thread-safe!
    .collect::<Vec<_>>();
```

### 3. Salsa LRU размеры

**Настройки для больших проектов:**

```rust
// Парсинг: держим больше файлов в кеше
#[salsa::tracked(lru = 512)]  // Вместо 128
fn parse(db: &dyn Db, file_id: FileId) -> Parse { ... }

// HIR: тоже увеличиваем
#[salsa::tracked(lru = 512)]
fn analyze(db: &dyn Db, file_id: FileId) -> Analysis { ... }

// Метаданные: маленький кеш (редко меняются)
#[salsa::tracked(lru = 16, durability = Durability::HIGH)]
fn load_configuration(db: &dyn Db) -> Arc<Configuration> { ... }
```

**Trade-off:**
- Больший LRU = больше памяти, меньше cache misses
- Меньший LRU = меньше памяти, больше перепарсивания

Для 4GB проекта: **LRU = 512** кажется оптимальным (256 MB кеша).

## Рекомендации для проектов 4GB+

### SonarQube Integration

✅ **Рекомендуется:**
- Full scan: ~2-5 минут (vs 13 часов на Java) — **160x улучшение**
- Память: ~1-2 GB (vs 80 GB) — подходит для CI/CD
- Параллелизм: использовать все доступные ядра

**Пример запуска:**
```bash
# CI/CD pipeline
bsl-analyzer analyze --project /path/to/project \
  --output sonarqube.json \
  --workers 8 \
  --memory-limit 2GB

# Ожидаемое время: 2-5 минут для 4GB проекта
```

### LSP для ежедневной работы

✅ **Отлично подходит:**
- Cold start: ~3-5 секунд (vs 5-10 минут)
- Incremental updates: < 50 ms (vs 500-5000 ms)
- Память: ~1-2 GB (vs 10-80 GB)

**User experience:**
```
Пользователь печатает →
  Изменение текста →
    Salsa invalidates parse →
      Reparse (17ms) →
        Diagnostics (30ms) →
          Update UI (5ms)

Total: ~52ms ✅ (незаметно для пользователя!)
```

### Ограничения и caveats

⚠️ **Потенциальные проблемы:**

1. **Первый full scan все еще занимает время**
   - 2-5 минут для 4GB — это быстро для batch, но не мгновенно
   - Решение: SonarQube может делать incremental scans

2. **Метаданные тоже могут быть большие**
   - Для огромных конфигураций (ERP 2.5) метаданные ~50-100 MB
   - Парсинг XML медленнее, чем BSL
   - Решение: Salsa кеширует с Durability::HIGH

3. **80,000 файлов — это много для индексации**
   - VFS должна отслеживать все файлы
   - Решение: используем эффективные структуры (DashMap, PathInterner)
