# CachedPublic

Статус: `done`, `needs-code-work`

Дата разбора: 2026-05-07

## Суть правила

Кэшируемый общий модуль, то есть модуль с повторным использованием
возвращаемых значений `DuringRequest` / `DuringSession`, не должен содержать
программный интерфейс. Публичный API лучше держать в обычном общем модуле, а
специализированный `ПовтИсп` / `Cached` модуль использовать как внутреннюю
реализацию.

Это не проверка корректности кэширования отдельных функций. Правило про
совместимость библиотек: потребители не должны зависеть от того, что конкретная
функция сейчас живет в специализированном кэшируемом модуле.

## Как реализовано

Handler работает через три cached-запроса:

- `ctx.region_tree()` ищет области с именем `ПрограммныйИнтерфейс` или
  `Public`;
- `ctx.module_metadata()` проверяет, что текущий файл относится к общему
  модулю и что `ReturnValuesReuse` равен `DuringRequest` или `DuringSession`;
- `ctx.item_tree()` проверяет, что внутри публичной области есть хотя бы одна
  процедура или функция.

Если все условия выполнены, диагностика выпускается на диапазон всей области.
Одна публичная область дает один diagnostic, даже если внутри несколько
методов. Quick-fix нет.

`ReturnValueReuse::Unknown` не считается кэшируемым режимом. Если файл похож на
модуль по пути, но конфигурационная metadata не загружена или общий модуль не
найден, диагностика ничего не сообщает.

## Что покрыто

- режимы `DuringRequest` и `DuringSession`;
- режим `DontUse` не считается кэшируемым;
- не-общий модуль и отсутствие metadata пропускаются;
- русская область `ПрограммныйИнтерфейс`;
- английская область `Public`;
- регистронезависимое сравнение имен публичных областей;
- непубличные области вроде `СлужебныйПрограммныйИнтерфейс`, `Private`,
  `Internal` не считаются нарушением этого правила;
- пустая публичная область не диагностируется;
- процедуры и функции внутри публичной области диагностируются;
- несколько публичных областей дают несколько diagnostics;
- несколько методов в одной публичной области дают один diagnostic.

Покрытие хорошее для текущей формулировки "публичная область с методами в
кэшируемом общем модуле".

## Пробелы покрытия

- Unit-тесты положительных сценариев используют `check_with_reuse()`, который
  подставляет `ReturnValueReuse` напрямую и обходит реальный путь
  `ctx.module_metadata()`. Единственный тест основного `check()` проверяет
  отрицательный случай без metadata. Поэтому интеграция с реальной metadata
  кэшируемого общего модуля покрыта слабо.
- Документация говорит про экспортные методы и программный интерфейс. Код
  фактически проверяет наличие любого метода внутри области
  `ПрограммныйИнтерфейс` / `Public`, не проверяя `Экспорт`. Это согласуется с
  областью как маркером API, но может удивлять, если в публичной области лежит
  неэкспортный метод. Соседняя диагностика `NonExportMethodsInApiRegion` уже
  считает такой метод отдельным нарушением.
- Проверка ищет только области с точным именем `ПрограммныйИнтерфейс` или
  `Public`. Если проект использует другой публичный раздел, настройку или
  ошибочное имя области, это правило его не увидит.
- В `RegionTree` уже есть понятие API-региона, включающее также
  `СлужебныйПрограммныйИнтерфейс` и `Internal`. Эта диагностика намеренно
  использует свой `is_public_region()`, но это расхождение важно держать
  явным: правило `#std644` запрещает именно внешний программный интерфейс в
  специализированном модуле, а не любые служебные API-области.
- Область диагностируется целиком. Для пользователя точнее было бы подсветить
  имя области или конкретные экспортные методы, но комментарий в коде говорит,
  что диапазон всей области сохранен ради совместимости с текущими тестами.
- Если публичная область вложена внутрь другой области, текущая проверка
  сработает по самой вложенной публичной области. Если наоборот метод лежит во
  вложенной непубличной области внутри корневого `ПрограммныйИнтерфейс`, он
  тоже попадает в диапазон публичной области и будет диагностирован. Это может
  быть правильной трактовкой root API region, но отдельного теста на вложенность
  именно с публичной областью нет.
- Стандарт `#std644` шире этой диагностики. Он говорит не только про кэшируемые
  модули, но и про другие специализированные модули, например `ВызовСервера`.
  `CachedPublic` покрывает только часть про модули с повторным использованием
  возвращаемых значений.
- `ReturnValueReuse::Unknown` пропускается. Для частично распарсенной или новой
  metadata это снижает риск ложных срабатываний, но может скрыть реальное
  нарушение.

## Может ли инфраструктура улучшить качество

Да. Нужные кирпичи уже есть:

- `ModuleMetadata` знает тип модуля и `ReturnValuesReuse`;
- `RegionTree` умеет искать корневой API region для диапазона метода;
- `ItemTree` знает методы, их диапазоны и признак `is_export`;
- test-utils уже умеют подставлять `ModuleMetadata` через
  `check_metadata_diagnostic()`, что можно использовать для main-path тестов.

Для этой диагностики не нужны CFG/dataflow. Улучшения лежат в точности
metadata-тестов, согласовании определения публичной области и UX диапазонов.

## Возможное объединение

Ближайшие соседи — правила про общие модули и API-регионы:
`CommonModuleNameCached`, `CommonModuleMissingAPI`,
`NonExportMethodsInApiRegion`, `PublicMethodsDescription`,
`CommandModuleExportMethods`, а также группа `CommonModuleName*`.

Объединять их в один diagnostic code не стоит: они проверяют разные стандарты и
разные проектные решения. Но общий внутренний слой был бы полезен: helper'ы для
классификации общих модулей (`cached`, `server-call`, `client`, `global`),
единое определение публичных/API-регионов и shared metadata test harness. Для
`CachedPublic` особенно важно не смешать "публичный API в кэшируемом модуле" с
проверками именования `ПовтИсп` и полноты описания публичных методов.

## Варианты снятия ограничений

1. Добавить main-path тесты через metadata provider: кэшируемый общий модуль с
   `ПрограммныйИнтерфейс`, обычный общий модуль, не-общий модуль,
   `ReturnValueReuse::Unknown`.
2. Явно решить, что диагностируется: вся область `ПрограммныйИнтерфейс` или
   только экспортные методы внутри нее. После решения синхронизировать текст
   rule-доков, сообщение и тесты.
3. Если остаемся на region-level диагностике, перейти на `region.name_range`
   или добавить secondary ranges на методы, когда инфраструктура LSP позволит
   сделать это без поломки UX.
4. Добавить тесты на вложенные области: публичная внутри непубличной,
   непубличная внутри публичной, несколько уровней вложенности.
5. Рассмотреть использование общего helper'а из `RegionTree` или нового
   helper'а `is_public_api_region_name`, чтобы определения `Public` /
   `ПрограммныйИнтерфейс` не расходились между диагностиками.
6. Не расширять `CachedPublic` на весь `#std644` механически. Для
   `ВызовСервера` и других специализированных модулей лучше отдельные
   диагностики или параметризованный общий слой, иначе название и сообщение
   правила станут неточными.
7. Для `ReturnValueReuse::Unknown` оставить permissive skip или добавить
   отдельный debug/config warning, если в реальных проектах metadata часто
   оказывается неполной.

## Вывод

Диагностика хорошо соответствует узкой части `#std644` про кэшируемые общие
модули и использует подходящую инфраструктуру: metadata + RegionTree + ItemTree.
Главный практический пробел — отсутствие положительного теста реального
metadata-пути. Второй важный вопрос — уточнить контракт: правило говорит про
экспортный API, а реализация сейчас диагностирует любую функцию или процедуру в
публичной области.
