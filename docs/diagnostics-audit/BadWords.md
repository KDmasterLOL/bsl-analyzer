# BadWords

Статус: `done`, `needs-code-work`

Дата разбора: 2026-05-07

## Суть правила

Диагностика ищет слова или выражения, запрещенные локальной политикой проекта.
Список задается параметром `badWords` как регулярное выражение. Поиск
регистронезависимый. Проверку комментариев можно настраивать через
`findInComments`.

Правило выключено по умолчанию: без проектного списка запрещенных слов оно не
имеет универсального смысла.

## Как реализовано

Есть два пути:

- `check_node()` вызывается из `collect_syntax_single_pass()` для каждого
  `SyntaxNode`;
- `check()` делает самостоятельный проход по `ctx.file_text()` построчно и
  используется текущими unit-тестами handler'а.

В обоих случаях:

- если диагностика отключена или `badWords` пустой, результат пустой;
- regex строится через `RegexBuilder::case_insensitive(true)`;
- некорректный regex молча отключает диагностику;
- каждое совпадение превращается в diagnostic без quick-fix.

Метаданные в локальном `v8std`: тип — дефект кода, важность — важный, включена
по умолчанию — нет, тег `design`, прямой стандарт не указан.

## Что покрыто

- пустой `badWords` фактически отключает правило;
- отсутствие совпадений;
- одно запрещенное слово;
- регистронезависимый поиск;
- несколько альтернатив через regex, например `TODO|FIXME|HACK`;
- `findInComments=false` для строки, которая начинается с `//`;
- точные диапазоны в standalone-проходе по тексту;
- поиск внутри BSL-кода, строк запросов, имен переменных и комментариев.

Для простого project-policy фильтра этого достаточно.

## Пробелы покрытия

- Unit-тесты вызывают `check()`, но общий diagnostic pipeline использует
  `check_node()` через single-pass AST. Это разные алгоритмы с разными рисками.
- `check_node()` сканирует `node.text()` каждого AST-узла. Одно и то же слово
  может попасть в несколько ancestor-узлов, что создает риск дублей в реальном
  запуске. Глобальная дедупликация сейчас применяется только к `UnreachableCode`.
- `check_node()` каждый раз заново читает параметры и компилирует regex. При
  включенном `BadWords` это дорого: стоимость становится примерно
  `количество AST-узлов * compile(regex)`.
- `findInComments=false` пропускает только текст, который после trim начинается
  с `//`. Inline-комментарий после кода не отделяется от кода и может быть
  просканирован.
- Диагностика сканирует весь текст, включая строковые литералы и SDBL-запросы.
  Это может быть желаемо для project-policy, но отдельной настройки
  "только идентификаторы / только комментарии / только строки" нет.
- Regex не оборачивается в границы слов. Короткий шаблон может срабатывать
  внутри нормальных идентификаторов или строк.
- Некорректный regex молча подавляет диагностику. Пользователь не получает
  diagnostic/config-warning о плохом параметре.
- В `docs/configuration/DIAGNOSTICS.md` пример `badWords =
  "хрень,костыль,тупой"` выглядит как список через запятую, но реализация
  ожидает regex. Для альтернатив нужен шаблон вида `хрень|костыль|тупой`.

## Может ли инфраструктура улучшить качество

Да. Для этой диагностики не нужны HIR, dataflow или metadata; достаточно
существующей line/text-инфраструктуры и diagnostic config.

Полезнее всего не усиливать семантику, а сделать запуск согласованным:

- один источник правды для сканирования текста;
- precompiled regex на один diagnostic run;
- явный режим областей поиска: code, comments, strings;
- конфигурационная ошибка для невалидного regex.

## Возможное объединение

Близкие по механике правила — все простые text/token checks:
`CommentedCode`, `DuplicateStringLiteral`, `LineLength`,
`ConsecutiveEmptyLines`, `SpaceAtStartComment`, `YoLetterUsage`,
`LatinAndCyrillicSymbolInWord`, частично `InvalidCharacterInFile`.
По смыслу `BadWords` остается отдельным project-policy правилом, потому что
набор слов и области поиска задаются проектом.

Объединять diagnostic codes не нужно. Полезное объединение здесь
инфраструктурное: общий token/text scanner на файл, precompiled per-run
параметры, единый режим "сканировать code/comments/strings" и общий слой
дедупликации диапазонов для single-pass диагностик.

## Варианты снятия ограничений

1. Убрать `BadWords` из node-based single-pass или переписать его на token/text
   pass, чтобы каждое место файла сканировалось ровно один раз.
2. Компилировать regex один раз на файл, а не на каждый AST-узел.
3. Добавить integration-тест через `crate::diagnostics()` с включенным
   `BadWords`, чтобы проверить отсутствие дублей в реальном пайплайне.
4. Сделать `findInComments` точным: определять COMMENT-токены, а не только
   строки, начинающиеся с `//`.
5. Добавить параметры области поиска, если это нужно пользователям:
   `findInStrings`, `findInIdentifiers`, `findInComments`.
6. Сообщать о невалидном regex через diagnostic-конфиг или отдельное warning
   сообщение, иначе правило выглядит как "не работает".
7. Исправить пример в `docs/configuration/DIAGNOSTICS.md` на regex с `|` или
   явно написать, что значение является regex, а не comma-separated list.

## Вывод

Правило простое и хорошо подходит для локальной project-policy проверки.
Сейчас основной риск не в самой идее, а в интеграции: production path через
`check_node()` потенциально дублирует срабатывания и компилирует regex слишком
часто. Следующий практичный шаг — привести `BadWords` к единому text/token pass,
добавить integration-тест реального пайплайна и поправить пример конфигурации.
