# AssignAliasFieldsInQuery

Статус: `done`, `needs-code-work`

Дата разбора: 2026-05-07

## Суть правила

Диагностика требует явно задавать псевдонимы выбранным полям запроса через
`КАК` / `AS`. Это снижает зависимость кода от автоматически сформированных имен
колонок результата и соответствует стандарту оформления текстов запросов.

Поля со звездочкой (`*`, `Таблица.*`) не требуют псевдонима. **Track 2 §4 Slice 2
(2026-05-10):** проверка распространена на каждую секцию `ВЫБРАТЬ` единообразно,
включая вторую и последующие части `ОБЪЕДИНИТЬ` — намеренное расхождение с BSL-LS,
который исторически исключал части UNION из проверки.

## Как реализовано

Это SDBL-диагностика. BSL lowering находит строковые литералы, которые
`looks_like_sdbl()` считает запросами, извлекает SDBL-текст, парсит его и
сохраняет `SdblQueryInfo`. Затем `sdbl_hir` строит HIR запроса и в
`check_alias_without_as_keyword()` выпускает `AliasWithoutAsKeyword`, если поле:

- не является `*` / `Таблица.*`;
- не содержит parse error;
- не находится в union-части;
- не имеет псевдонима вообще или имеет неявный псевдоним без `КАК` / `AS`.

Handler `assign_alias_fields_in_query` только преобразует SDBL-диагностику в IDE
diagnostic, мапит диапазон обратно в BSL-строку и строит quick-fix:

- для поля без псевдонима вставляет ` КАК <raw_name>`;
- для неявного псевдонима вставляет `КАК ` перед именем псевдонима.

## Что покрыто

- явный `AS` / `КАК`;
- поле без псевдонима;
- неявный псевдоним без `AS` / `КАК`;
- русские и английские ключевые слова;
- несколько полей с разными состояниями в одном SELECT;
- `*` и `Таблица.*`;
- комментарии внутри запроса;
- `ОБЪЕДИНИТЬ` / `ОБЪЕДИНИТЬ ВСЕ` с проверкой только первой части;
- несколько отдельных запросов в одном BSL-файле;
- вложенный SELECT в источнике данных;
- `ПЕРВЫЕ` / `TOP`, `РАЗЛИЧНЫЕ` / `DISTINCT`;
- ведущая пустая строка в многострочной BSL-строке.

Покрытие сильное для простых и средних SELECT-запросов, включая маппинг из
многострочной BSL-строки в SDBL-диапазон.

## Пробелы покрытия

- В комментариях handler и в rule-доках есть терминологическая путаница:
  написано, что проверяются поля "в подзапросах", но фактическая реализация и
  тесты проверяют основной SELECT тоже. В SDBL AST слово `subquery` означает
  контейнер main query + union, а не только вложенный подзапрос.
- Union-части не проверяются. Это соответствует текущему поведению, но стандарт
  `#std437` формулирует требование к тексту запроса в целом, а не только к первой
  части объединения.
- Диагностика видит только строковые литералы, которые начинаются с
  `SELECT` / `ВЫБРАТЬ` или `DROP` / `УНИЧТОЖИТЬ`. Запросы, собранные через
  конкатенацию, шаблоны, переменные или `СтрЗаменить`, покрываются только если
  отдельный литерал сам выглядит как полноценный запрос.
- Parser/HIR пропускает поля с parse error, поэтому при частично неподдержанном
  синтаксисе диагностика может молча не сработать.
- `raw_name` для quick-fix берется как последний `IDENT` в выражении. Для
  функций, агрегатов, выражений `CASE`, литералов и параметров автопсевдоним
  может быть неочевидным или отсутствовать, поэтому fix не всегда доступен или
  не всегда семантически лучший.
- Тексты `v8std #437` также требуют общего форматирования запроса, комментариев
  и структурирования. Эта диагностика покрывает только пункты про псевдонимы
  выбранных полей и `КАК`, не весь стандарт.

## Может ли инфраструктура улучшить качество

Да, но улучшения лежат в SDBL-стеке, а не в самом handler:

- SDBL extraction уже кэшируется через Salsa и используется всеми SDBL
  диагностиками;
- single-pass dispatch в `runner.rs` уже прогоняет все SDBL handler'ы за один
  проход по HIR-диагностикам;
- parser хранит явный признак наличия `AS` / `КАК` у alias;
- source mapper уже учитывает многострочные BSL-строки, `|` и экранированные
  кавычки;
- SDBL HIR содержит field-level данные (`alias`, `raw_name`, `has_as_keyword`,
  `has_parse_error`, `diagnostic_range`), которых достаточно для более точных
  сообщений и fixes.

## Возможное объединение

Эта диагностика естественно относится к группе SDBL/query-правил:
`QueryParseError`, `SelectTopWithoutOrderBy`, `FieldsFromJoinsWithoutIsNull`,
`FullOuterJoinQuery`, `JoinWithSubQuery`, `JoinWithVirtualTable`,
`LogicalOrInJoinQuerySection`, `LogicalOrInTheWhereSectionOfQuery`,
`IncorrectUseLikeInQuery`, `UsingLikeInQuery`,
`VirtualTableCallWithoutParameters`, `QueryNestedFieldsByDot`,
`QueryToMissingMetadata`.

Объединять все эти правила в один пользовательский `DiagnosticCode` не стоит:
они про разные стандарты, разную важность и разные fixes. Но есть смысл держать
единый SDBL diagnostic engine: один extraction/parse/lower pass, общая
обработка parse-error recovery, общий source mapper и shared test fixtures для
многострочных запросов. Для `#std437` можно отдельно оценить, не собрать ли
несколько форматных query-правил под общий внутренний модуль, оставив внешние
коды раздельными.

## Варианты снятия ограничений

1. Уточнить документацию и комментарии: правило проверяет selected fields в
   main SELECT каждого SDBL select-блока, а не только вложенные подзапросы.
2. Решить продуктово, надо ли проверять union-части. Если да — убрать skip по
   `is_union` или сделать параметр диагностики для совместимости.
3. Расширить извлечение запросов: поддержать простые случаи присваивания через
   конкатенацию строковых литералов и типовые шаблоны `СтрЗаменить`, не пытаясь
   выполнять произвольный BSL-код.
4. Улучшить генерацию quick-fix: для сложных выражений предлагать безопасный
   placeholder вроде `КАК ИмяПоля`, а не пытаться вывести имя из последнего
   идентификатора.
5. Добавить тесты на сложные выражения: агрегаты, `ВЫБОР ... КОНЕЦ`, параметры
   `&Параметр`, литералы, временные таблицы и многострочные строки с
   экранированными кавычками до диагностируемого поля.
6. Добавить regression-тест на соответствие количества `sdbl_hir_in_file()` и
   `all_sdbl_in_file()` для файлов с ошибочными запросами, потому что dispatch
   сейчас сопоставляет эти коллекции через `zip`.

## Вывод

Диагностика хорошо обоснована стандартом `#std437` и уже имеет полезный quick-fix.
Сам handler простой и выглядит устойчивым. Основной риск качества — полнота и
точность SDBL parser/extractor: если запрос не извлечен, не распарсен или поле
помечено parse error, правило не сможет сработать. Следующий практичный шаг —
сначала синхронизировать документацию с фактическим поведением, затем решить
вопрос union-частей и добавить тесты на сложные SELECT-выражения.
