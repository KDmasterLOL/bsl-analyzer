# AllFunctionPathMustHaveReturn

Статус: `done`, `needs-code-work`
Track 1 closure: E `49498d7d`, I `00da9fc8`, foundation `819945b7` — см. `docs/diagnostics-audit/TRACK_1_CLOSURE.md`.

Дата разбора: 2026-05-07

## Суть правила

Диагностика ищет функции, где есть достижимый путь выполнения до
`КонецФункции` без явного `Возврат`. Если возврат `Неопределено` задуман, он
должен быть написан явно.

Сейчас правило разделено с `FunctionShouldHaveReturn`: если в функции вообще нет
`Возврат`, HIR-lowering эмитит `FunctionShouldHaveReturn`; если хотя бы один
`Возврат` есть, эмитится кандидат `MissingReturn`, который обработчик
`AllFunctionPathMustHaveReturn` дополнительно проверяет по CFG.

## Как реализовано

Обработчик берет `MethodId`, получает `Body` и модульный CFG через
`ctx.module_cfgs()`, затем смотрит входящие ребра в `exit_point`.

Путь считается корректно завершенным, если последний оператор соответствующего
basic block — `Stmt::Return` или `Stmt::Raise`. Ребра `AdjacentCode`
игнорируются как мертвый код. Для `Conditional` ложная ветка без `Иначе`
считается пропущенным возвратом. Для `While`, `For`, `ForEach` ложная ветка
цикла сейчас считается допустимой.

Метаданные в локальном `v8std` совпадают с нашим intent: тип — дефект кода,
важность — важный, включена по умолчанию, теги `unpredictable`, `badpractice`,
`suspicious`, прямой стандарт не указан.

## Что покрыто

- функция с `ИначеЕсли` без финального `Иначе`;
- ветка `ИначеЕсли`, где есть вызов, но нет `Возврат`;
- явный `Возврат Неопределено`;
- `Если/Иначе`, где обе ветки возвращают значение;
- `Попытка/Исключение`, где обе ветки возвращают значение;
- `Если` без `Иначе`, после которого идет `Попытка/Исключение` и финальный
  `Возврат`;
- `ВызватьИсключение` как терминатор функции;
- процедуры не проверяются.

Покрытие хорошее для обычных ветвлений и части `try/except` сценариев.

## Пробелы покрытия

- Тесты для `Для каждого` и `Пока Истина` сейчас не фиксируют ожидаемое
  поведение: они принимают текущее состояние без assert по диагностике.
- CFG-builder содержит TODO для точного моделирования `break`, `continue` и
  `goto`; из-за этого диагностика может ошибаться на функциях с нетривиальным
  выходом из цикла или переходами по меткам.
- Ложная ветка циклов считается допустимой, хотя для обычного `Пока`, `Для` и
  `Для каждого` путь "цикл не выполнился ни разу" часто означает реальный путь
  без возврата.
- Нет явного учета конфигурационного смысла `loopsExecutedAtLeastOnce` в самом
  обработчике: CFG умеет включать/выключать loop-iteration edges, но решение
  диагностики сейчас зашито в локальные проверки входящих ребер.
- `#Если/#ИначеЕсли/#Иначе` представлены в CFG, но для этой диагностики не
  видно отдельной матрицы тестов на препроцессорные ветки и активные символы.
- Исключения моделируются только через явный `Raise`; возможные runtime
  исключения от обычных выражений не являются частью анализа, что нормально для
  статической диагностики, но это ограничение нужно считать осознанным.

## Может ли инфраструктура улучшить качество

Да. У проекта уже есть подходящие кирпичи:

- HIR-body дает структурные `Stmt` без хрупкого обхода AST;
- модульные CFG кэшируются через `module_cfgs`, поэтому усиление проверки не
  должно требовать построения графа на каждый handler-вызов;
- `ControlFlowGraph` уже умеет обходы `reverse_postorder` и
  `postorder_from_exit`;
- `AdjacentCode` уже отделяет мертвые ребра от живого потока;
- рядом есть dataflow-инфраструктура, если понадобится вынести свойство
  "path terminates" в общий анализ.

## Возможное объединение

Ближайшая пара — `FunctionShouldHaveReturn`. Сейчас разделение выглядит скорее
техническим, чем пользовательским: одна диагностика ловит функции без любого
`Возврат`, другая — функции, где `Возврат` есть не на всех путях. Для
пользователя это одна тема: "функция должна явно возвращать значение на каждом
живом пути".

Полное объединение кодов может быть breaking change для настроек и suppression.
Более безопасный вариант — общий HIR/CFG-анализ возвратов с двумя diagnostics
на выходе: сохраняем отдельные `DiagnosticCode`, но убираем дублирование
логики, синхронизируем документацию и тестовую матрицу. В документации можно
добавить cross-link между правилами или общую страницу "возвраты функций".

## Варианты снятия ограничений

1. Заменить эвристику "смотреть только входящие ребра в `Exit`" на общий анализ
   живых путей: все достижимые пути до `Exit` должны проходить через
   `Return/Raise`, а `AdjacentCode` не должен участвовать в решении.
2. Добавить loop-context в CFG-builder и корректно соединять `break` с выходом
   из текущего цикла, `continue` с заголовком цикла, `goto` с целевой меткой.
3. Явно определить семантику циклов для этой диагностики: консервативно считать
   false-branch цикла путем без возврата, кроме доказанных бесконечных циклов.
4. Добавить минимальный constant-condition анализ для `Пока Истина` и, возможно,
   `Если Истина/Ложь`, чтобы не плодить ложные срабатывания после пункта 3.
5. Зафиксировать тестовую матрицу: `while` с возможным нулем итераций,
   `foreach` по потенциально пустой коллекции, `break`, `continue`, `goto`,
   препроцессорные ветки, вложенные `try/except`.
6. Вынести повторно используемое свойство "блок/путь завершает выполнение
   метода" в CFG/dataflow-слой, чтобы этим могли пользоваться
   `UnreachableCode`, транзакционные диагностики и будущие flow-sensitive
   правила.

## Вывод

Диагностика уже существенно лучше простой AST-проверки: она использует HIR и CFG
и закрывает основные ветвления. Основной риск качества сейчас в неточности CFG
для управляющих операторов и в слишком локальном алгоритме проверки. Следующий
практичный шаг — не переписывать правило целиком, а сначала усилить CFG для
`break/continue/goto` и добавить assert-тесты на текущие незафиксированные
цикловые кейсы.
