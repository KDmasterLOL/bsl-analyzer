# Модель объединения overlay

## Главный инвариант

Результат поиска по workspace должен соответствовать не просто baseline и не
просто локальному состоянию файловой системы, а их логическому объединению:

```text
selected baseline snapshot + local overlay
```

## Операции overlay

Overlay должен поддерживать три сценария.

### 1. Добавление

Если файл есть локально, но отсутствует в baseline:

- он попадает в результат только из overlay.

### 2. Замена

Если путь есть и в baseline, и локально, но содержимое изменилось:

- baseline-хиты по этому пути скрываются;
- в результат попадают только локальные хиты.

### 3. Удаление

Если файл был в baseline, но локально удалён:

- baseline-хиты по нему больше не должны быть видны.

## Объединение для полнотекстового поиска

Упрощённый алгоритм:

1. запросить baseline-хиты полнотекстового поиска;
2. запросить overlay-хиты полнотекстового поиска;
3. отфильтровать baseline-хиты по скрытым и замещённым путям;
4. объединить результаты;
5. нормализовать score и отсортировать итоговый ответ.

## Объединение для семантического поиска

Алгоритм аналогичен полнотекстовому, но источник baseline-хитов — semantic
serving в PostgreSQL, а источник overlay-хитов — локальный семантический контур.

## Почему merge не в SQL

Потому что overlay — это текущее локальное состояние рабочей копии, включая
незакоммиченные изменения. Отправлять его на сервер ради каждого запроса или
каждого изменения нецелесообразно.

Объединение в приложении лучше отражает продуктовую модель:

- shared baseline — общий и стабильный;
- overlay — приватный и часто меняющийся.

## Что обязательно должно соблюдаться

- локальная замена файла должна побеждать baseline по path semantics;
- локальное удаление должно скрывать baseline-хиты;
- новый локальный файл должен участвовать в поиске без публикации в общий backend.
