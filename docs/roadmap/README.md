# Roadmap

Направления развития bsl-analyzer. Документы здесь — не план работ
с дедлайнами, а зафиксированные приоритеты и обоснования: что считаем
важным, в каком порядке, и почему.

## Архитектурные принципы

Любая новая работа должна укладываться в существующие границы. Если
кажется, что нужно их нарушить — это сигнал пересмотреть подход, а не
архитектуру.

1. **Lazy через Salsa, инкрементальная инвалидация.** Ничего не
   вычисляется проактивно по умолчанию; кэшируемые значения подвержены
   LRU-эвикции; изменение одного файла инвалидирует только связанные
   query.
2. **Два контура — LSP-интерактив и streaming/CLI — раздельно.**
   Общий traits-интерфейс (`AnalysisProvider`), но разные движки и
   разные стратегии кэширования. Не сливать обратно в один путь.
3. **Семантическая глубина важнее структурной полноты.** Закрывать
   дыры типизации и качества диагностик приоритетнее, чем расширять
   перечень фич LSP.
4. **Pull-режим и фоновый прогрев — поверх Salsa.** Никаких отдельных
   batch-движков ради LSP-фич; всё реализуется как фоновые воркеры
   над общей БД с rate-limit и LRU-эвикцией.

## Что НЕ в приоритете

Зафиксировано отдельно, чтобы не возвращаться к этим вопросам без
явного триггера:

- **Proactive prewarm всего проекта при `initialize`.** Противоречит
  lazy-модели и не даёт пользовательской выгоды: интерактивный
  пользователь не открывает 25K файлов одновременно. Прогрев — только
  опциональный фоновой через `prime_caches`.
- **Eager-вычисление и удержание ParseTree/SymbolTree для всех файлов
  workspace.** Salsa + LRU делают это автоматически по фактическому
  использованию.
