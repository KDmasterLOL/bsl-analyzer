# LSP features roadmap

Расширение LSP-возможностей сверх текущего push-based pipeline.
Все нижеперечисленное реализуется поверх существующей Salsa-БД,
без отдельных batch-движков.

## Pull-режим для диагностик

### Контекст

Текущий пайплайн — push-only: `publishDiagnostics` рассылается
сервером при `didOpen`/`didChange`. У клиента нет способа сказать
«дай мне всё, что у тебя есть по этому файлу прямо сейчас» или
«пройдись по проекту и отдай отчёт». Это ограничивает интеграции,
которым нужен явный контроль над моментом сбора диагностик — например,
CI-extension редактора, batch-просмотр, generation-time проверки.

### `textDocument/diagnostic`

Тривиально. Те же диагностические query, что используются в push-режиме,
вызываются синхронно в ответ на pull-запрос. Salsa-кэш переиспользуется
полностью.

### `workspace/diagnostic`

Полный отчёт по проекту через pull. Реализация: **in-process фоновый
воркер**, обходящий файлы пакетами, rate-limited, использующий ту же
Salsa-БД, что и интерактив.

**Принципы:**

- Один воркер на сессию (не плодить параллельные обходы).
- Pacing через `crossbeam_channel` + token bucket — не блокировать
  hot-path LSP-ответов.
- Кэш не «греется намеренно» — воркер просто обращается к существующим
  query, Salsa решает что вычислить и что эвиктить.
- Отчёт стримится клиенту батчами (`previousResultIds` для дельт).

**Не делать через subprocess.** Subprocess (как для CLI/Sonar-режима)
теряет Salsa-кэш и не подходит для интерактивной LSP-сессии — клиент
запрашивает `workspace/diagnostic` повторно, и каждый раз должен
получать дешёвый результат за счёт кэша.

## Опциональный `prime_caches` — узко, только для индекса символов

### Что НЕ прогревать

Проактивный обход `parse`/`item_tree`/`symbol_tree`/`infer`/dataflow
по всем файлам проекта — **противоречит нашей lazy-модели** и убивает
основное преимущество в памяти. Интерактивный пользователь не открывает
25K файлов сразу; прогревать их на случай — значит держать в куче то,
что никогда не понадобится.

Зафиксировано как принцип: эти query вычисляются **только по факту
обращения** через LSP-запросы пользователя, Salsa-кэш растёт по
актуальному использованию и эвиктится LRU.

### Где прогрев потенциально оправдан

Единственный pre-build, у которого есть честный обоснованный профит, —
**`module_symbols` для FST-индекса workspace symbols** (см.
[workspace-symbols.md](workspace-symbols.md)). Без него первый `Ctrl+T`
после старта на больших конфигурациях будет ждать ~1-3 секунды
параллельного обхода модулей.

И даже здесь дефолт — **lazy**: первый `Ctrl+T` платит цену, дальше
мгновенно. Прогрев становится опцией только при подтверждённой
неприемлемости первой задержки на конкретных пользовательских кейсах.

### Поведение, если включается

- **По умолчанию выключено.** Включается через
  `bsl-analyzer.cachePriming.enable`.
- Запускается **в фоновом rayon-пуле**, не блокирует LSP-ответы.
- Прогревается **только `module_symbols`**, ничего больше.
- Прогретые значения попадают в Salsa-кэш на общих основаниях,
  подвержены LRU-эвикции.

### Бюджет памяти

FST workspace symbols на ERP: ~10-20 MB при полностью прогретом
состоянии. Это укладывается в существующий профиль; никакого
размена «больше памяти за интерактивность» здесь нет — мы не
накапливаем тяжёлые структуры (`parse`/`infer`).

## Hover/completion полировка

Не отдельная фича, скорее набор мелких улучшений, которые
естественно ложатся в общий путь:

- **Hover для chained-выражений с union-типами.** Сейчас union
  отображается как «`Строка | Число`» — стоит улучшить форматирование
  для длинных union'ов из платформенных типов.
- **Completion ранжирование по «частоте использования в проекте»**
  (нужен лёгкий счётчик в `WorkspaceSymbols`).
- **Snippet completion** для частых конструкций (`Если…Тогда…КонецЕсли`,
  `Для Каждого…Цикл`, шаблоны запроса).

## Capabilities, которые НЕ берём в работу

- **`textDocument/inlineValue`** (debug-only, BSL отлаживается через
  Конфигуратор/EDT — не наш профиль).
- **`textDocument/inlayHint` для типов параметров** — спорно, BSL-код
  и так визуально плотный, type-hints могут мешать; вернуться к
  вопросу после Tier 1 типизации.
- **Notebook support** — не наш кейс.
