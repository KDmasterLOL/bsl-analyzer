# Dataflow-анализ в BSL Analyzer

Этот документ описывает **текущее** состояние dataflow-подсистемы в проекте:
зачем она нужна, на каких крейтах построена и какие диагностики уже завязаны на
flow-sensitive анализ.

## Зачем это нужно

Часть диагностик нельзя надёжно реализовать простым локальным обходом AST.
Нужен анализ потока управления и информации о том, как значения и определения
переменных распространяются по ветвлениям, циклам и выходам из метода.

Примеры таких задач:

- найти локальную переменную, которой значение присваивается, но потом не читается;
- понять, какие определения переменной достигают конкретного вызова `СтрШаблон`;
- отследить параметры метода, которые были перезаписаны до первого чтения.

## Из чего состоит подсистема

Dataflow опирается на несколько слоёв.

```text
HIR / Body
  → CFG (`cfg`, `cfg-types`)
  → dataflow engine (`dataflow`)
  → Salsa-кэширование (`ide-db` / `ide`)
  → diagnostics (`ide-diagnostics`)
```

### `cfg`

Строит control-flow graph по телу метода.

### `dataflow`

Содержит generic engine и конкретные анализы:

- reaching definitions;
- liveness analysis.

### `ide-diagnostics`

Использует результаты dataflow либо напрямую, либо через flow-sensitive
collector.

## Какие анализы реализованы

### Reaching definitions

Определяет, какие присваивания/объявления переменной могут достигать заданной
точки программы.

Это используется там, где диагностика должна понимать, **откуда взялось текущее
значение**, а не просто видеть синтаксическое имя переменной.

### Liveness analysis

Определяет, может ли значение переменной быть прочитано на каком-либо пути
выполнения после данной точки программы.

Это базовый инструмент для поиска неиспользуемых локальных переменных и других
похожих задач.

## Как это связано с Salsa

Результаты dataflow не пересчитываются без необходимости. Они кэшируются как
часть общей системы запросов проекта. Это означает:

- изменение одного метода не должно пересчитывать весь проект;
- LSP и CLI переиспользуют уже готовые результаты;
- тяжёлые flow-sensitive вычисления остаются приемлемыми по latency.

## Актуальное использование в диагностиках

На текущий момент подтверждено по коду следующее.

### Диагностики, которые напрямую используют dataflow API

- `UnusedLocalVariable` — использует module-level liveness;
- `IncorrectUseOfStrTemplate` — использует reaching definitions;
- `RewriteMethodParameter` — использует module-level reaching definitions.

### Диагностики, которые выполняются в flow-sensitive collector

- `UnreachableCode`
- `UnusedLocalVariable`
- `UnusedParameters`
- `MissingTemporaryFileDeletion`
- `MissingTempStorageDeletion`

## Конфигурация

У dataflow есть один ключевой runtime-параметр:

```toml
[diagnostics]
dataflowMaxIterations = 20000
```

Что он делает:

- ограничивает число итераций до сходимости для dataflow-анализа;
- нужен как защитный предел для очень сложных методов;
- по умолчанию используется значение `10000`.

Важно: в Rust-структурах поле называется `dataflow_max_iterations`, но в
`bsl-analyzer.toml` используется ключ `dataflowMaxIterations`.

## Что считается текущим design intent

Подсистема развивается как общий reusable слой, а не как набор отдельных
одноразовых эвристик в каждой диагностике. Это означает:

- новые flow-sensitive проверки по возможности должны опираться на общий engine;
- ad-hoc анализ лучше заменять на reusable lattice/transfer-основанные решения;
- диагностики должны получать уже готовые результаты из dataflow-API, а не
  пересобирать похожий анализ локально.

## Ограничения

Несмотря на зрелость подсистемы, это всё ещё не «универсальный анализатор всего
на свете». Практические ограничения остаются такими:

- часть диагностик по-прежнему проще и дешевле реализовать без CFG/dataflow;
- сложные merge- и alias-сценарии могут потребовать новых анализов, а не только
  reaching definitions и liveness;
- слишком агрессивное расширение flow-sensitive слоя без замеров может ударить
  по latency CLI и LSP.
