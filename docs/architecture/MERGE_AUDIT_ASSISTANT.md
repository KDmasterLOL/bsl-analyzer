# Архитектурная заметка: merge-audit assistant для 1С

**Статус:** proposal  
**Дата:** 2026-04-21

Этот документ фиксирует практическое направление развития `bsl-analyzer` в сторону
умного помощника для сравнения и аудита обновлений конфигураций 1С.

Речь не про "ещё один diff", а про инструмент, который помогает разбирать
типовой сценарий обновления:

```text
старый vendor/base + наши доработки + новый vendor + develop/contractor
```

и отвечает на вопрос:

- что реально потеряно;
- что просто переместилось;
- что уже закрыто новой поставкой;
- где остался только визуальный / структурный шум.

## Почему это направление полезно

Практика обновлений 1С плохо ложится на обычный `git diff` и даже на аккуратный
ручной merge.

Основные причины:

- логика одной доработки часто размазана по нескольким файлам объекта;
- потери происходят не только на уровне процедур, но и на уровне отдельных вызовов;
- формы и XML часто генерируют большой объём визуального шума;
- часть бизнес-изменений выглядит как небольшая правка условия, а не как новый блок;
- в одном merge одновременно смешиваются поставка, локальные изменения и адаптация под новую версию.

Из-за этого даже после нескольких проходов ревью можно продолжать находить:

- потерянные вызовы;
- потерянные присваивания реквизитов;
- пропавшие блоки заполнения табличных частей;
- расхождения по модели блокировок;
- различия, которые текстово выглядят мелкими, но поведенчески значимы.

## Почему `bsl-analyzer` подходит для этой задачи

В проекте уже есть сильная база, достаточная для первого полезного MVP:

- full-fidelity parser / syntax tree;
- HIR и семантические представления модулей;
- `call_graph`-факты по модулям;
- загрузка Designer-метаданных через `bsl-metadata`;
- `ide-db` с пониманием типов модулей и путей объектов;
- поиск и модель `baseline + overlay`, близкая по смыслу к задаче merge-аудита;
- MCP и CLI как готовые каналы выдачи результата.

Это означает, что проекту не нужен отдельный новый анализатор. Нужен новый слой:

```text
parse + metadata + semantics + diff policy + merge findings
```

## Главная продуктовая цель

Новый режим должен помогать не "слить версии", а находить рискованные потери и
давать ревью-представление по объекту 1С.

Желаемый UX:

```text
bsl-analyzer merge-audit \
  --base <path-or-ref> \
  --ours <path-or-ref> \
  --theirs <path-or-ref> \
  --result <path-or-ref> \
  --object Documents/ЭтапПроизводства2_2
```

На выходе не сырой diff, а findings:

- High: потерян вызов `ПодобратьТребования(...)` в `ОбработкаЗаполнения`;
- Medium: исчез вызов `ОтменитьПроведениеКорректировкиНазначения()` в `ОбработкаУдаленияПроведения`;
- Low: `Forms/*/Ext/Form.xml` отличаются только визуальными параметрами таблиц.

## Что именно должен делать merge-audit assistant

### 1. Поддерживать 3-way и 4-way сравнение

Минимум:

- `base` — старая общая точка;
- `ours` — наша ветка / develop / локальная версия;
- `theirs` — новый vendor или подрядческая версия;
- `result` — текущий итог merge.

Инструмент должен уметь отвечать на вопросы:

- блок был в `ours`, есть ли он в `result`;
- блок был и в `ours`, и в `theirs`, не потерян ли он в `result`;
- блок был только в `theirs`, перенесли ли мы его;
- блок отсутствует в `result`, но уже покрыт новой поставкой другим кодом;
- изменение в `result` — это потеря, перенос или просто рефакторинг.

### 2. Работать на уровне объекта 1С, а не только одного файла

Для документа или справочника "логика объекта" обычно распределена по:

- `Ext/ObjectModule.bsl`;
- `Ext/ManagerModule.bsl`;
- `Forms/*/Ext/Form/Module.bsl`;
- `Forms/*/Ext/Form.xml`;
- `<Object>.xml`;
- `Commands/*/Ext/CommandModule.bsl`;
- шаблонам / правам / связанным XML.

Поэтому сравнение должно уметь строить объектный контекст:

```text
Document Object = metadata xml + code modules + form modules + form xml + commands
```

### 3. Уметь строить семантический diff для `.bsl`

Полезный diff для модулей — это не текст, а набор фактов:

- список процедур/функций;
- сигнатуры и экспортность;
- список вызовов внутри процедуры;
- чтение/запись реквизитов и табличных частей;
- присваивания бизнес-значимых полей;
- использование блокировок, фоновых заданий, обмена данными, привилегированного режима;
- условия, которые охраняют выполнение блока.

Минимальный полезный слой фактов:

- `procedure_presence`
- `call_presence`
- `field_write_presence`
- `field_read_presence`
- `guard_condition_summary`

### 4. Для XML и форм уметь отделять шум от смысла

Для `Form.xml` и других XML нужен режим, который умеет различать:

- визуальный шум;
- изменения состава объектов;
- изменения событий / команд / реквизитов / DataLockFields / подчинённости.

Примеры полезной классификации:

- `visual_only`
- `metadata_shape_changed`
- `command_set_changed`
- `data_lock_changed`
- `form_logic_link_changed`

Отдельно важен фильтр для форм, чтобы такие вещи не считались потерей логики:

- `HorizontalLines`;
- `VerticalLines`;
- `UseAlternationRowColor`;
- порядок элементов без изменения состава.

### 5. Выдавать findings, а не diff dump

Итог должен быть ближе к code review:

- severity;
- где именно потеря;
- откуда она ожидается (`ours`, `theirs`, `both`);
- почему это выглядит значимым;
- короткая рекомендация.

Пример формата:

```text
High
Object: Documents/ЭтапПроизводства2_2
File: Ext/ObjectModule.bsl
Procedure: ОбработкаЗаполнения
Issue: lost_call
Details: `ПодобратьТребования(...)` был в `ours` и `theirs`, отсутствует в `result`.
Why it matters: влияет на подбор требований и заполнение аналогов.
```

## Какой MVP имеет смысл делать

### Этап 1. Модульный 3-way аудит для `.bsl`

Самый практичный первый шаг:

- вход: четыре версии одного `.bsl` файла;
- разбиение на процедуры/функции;
- сравнение набора процедур;
- сравнение набора вызовов внутри процедур;
- отчёт по подозрительным потерям.

На этом этапе не нужен авто-merge. Нужен надёжный аудит.

### Этап 2. Object-level grouping

Добавить группировку файлов в объект 1С:

- модуль объекта;
- модуль менеджера;
- form modules;
- form xml;
- основной xml объекта.

И уметь запускать merge-аудит не по файлу, а по объекту.

### Этап 3. XML / metadata diff with noise filtering

Добавить специальные дифферы:

- `Form.xml`;
- `<Object>.xml`;
- `Rights.xml`;
- `CommandInterface.xml`;
- другие часто конфликтующие XML.

Главная цель этапа — резко снизить шум и подсветить реально значимые изменения.

### Этап 4. Ранжирование риска

После появления достаточного количества фактов можно добавлять скоринг риска.

Высокий риск:

- потерян вызов бизнес-метода;
- потерян вызов записи серии / требований / блокировки / фонового задания;
- исчезло присваивание реквизита, который потом используется;
- изменились `DataLockFields` или модель блокировки.

Средний риск:

- исчез блок заполнения упаковки / характеристик / аналитик;
- изменилась структура команд или подчинённости.

Низкий риск:

- перестановка кода;
- whitespace / comments only;
- визуальные параметры форм.

### Этап 5. MCP / AI presentation layer

После стабилизации CLI-режима это естественно выводить в MCP-инструмент:

- `merge_audit_object`
- `merge_audit_module`
- `merge_audit_findings`

Тогда AI-клиент сможет не просто искать по коду, а помогать разбирать обновления 1С в терминах риска.

## Рекомендуемая архитектура внутри проекта

### Новый доменный слой

Имеет смысл завести отдельный crate, например:

```text
crates/merge-audit
```

Ответственность слоя:

- загрузка нескольких версий одного объекта / файла;
- нормализация структуры для сравнения;
- вычисление merge-фактов;
- генерация findings.

### Что переиспользовать

Из уже существующего:

- `parser`, `syntax` — для full-fidelity структуры;
- `hir-def` / `hir` — для процедур, тел и вызовов;
- `call_graph` — как основу call-level diff;
- `bsl-metadata` — для объектной группировки и XML-понимания;
- `ide-db` — для определения типов модулей и привязки к MDO;
- `mcp-server` — для выдачи результатов наружу;
- `bsl-search`-модель `baseline + overlay` — как референс для resolved view между версиями.

### Что нужно добавить в `hir-def` / `hir`

Минимально полезные новые факты:

- per-procedure summary of local calls;
- summary of qualified module calls;
- writes to object fields / tabular parts;
- reads of object fields / tabular parts;
- use of selected platform primitives:
  - `БлокировкаДанных`
  - `ФоновыеЗадания.Выполнить`
  - `УстановитьПривилегированныйРежим`
  - `ОбменДанными.Загрузка`
  - `СообщитьПользователю`

### Что нужно добавить в `bsl-metadata`

Полезно уметь строить `ObjectBundle`:

```text
ObjectBundle {
  object_xml,
  object_module,
  manager_module,
  form_modules[],
  form_xmls[],
  commands[],
  extra_related_files[]
}
```

Это даст правильную единицу анализа для 1С.

## Какие эвристики стоит заложить сразу

### 1. Потеря процедуры

Если процедура была в `ours` и отсутствует в `result`, это не всегда баг.
Нужно проверять:

- остался ли вызов;
- появилось ли эквивалентное поведение под другим именем;
- не покрыла ли это новая поставка.

### 2. Потеря вызова важнее потери комментария

Приоритизировать не текстовое отличие, а:

- исчезновение вызова;
- исчезновение присваивания;
- изменение условия выполнения;
- изменение блокировки.

### 3. Использование без заполнения

Очень полезная эвристика для 1С:

- реквизит / локальная переменная активно используется ниже;
- но блок её заполнения исчез в `result`.

Это как раз тот тип ошибки, который плохо виден в обычном diff.

### 4. XML visual noise suppression

Для `Form.xml` и смежных файлов нужен список known-noise паттернов.

Иначе findings утонут в визуальном мусоре.

## Что не стоит обещать

Важно заранее зафиксировать границы:

- инструмент не должен обещать fully automatic correct merge;
- строковые вызовы, рефлексия и часть динамики 1С останутся серой зоной;
- сложные equivalence-сценарии между старой и новой поставкой будут требовать эвристик, а не строгих доказательств;
- формы полностью автоматически интерпретировать не получится.

При этих ограничениях merge-audit assistant остаётся advisory-слоем поверх git и EDT/Designer.

## Практический план внедрения

### Итерация 1

- новый crate `merge-audit`;
- CLI-команда для одного `.bsl` файла;
- 3-way / 4-way compare;
- findings по presence / absence процедур и вызовов.

### Итерация 2

- object bundle по Designer-структуре;
- merge-аудит по объекту 1С;
- поддержка `ObjectModule` + `ManagerModule` + form modules.

### Итерация 3

- XML-aware diff;
- form noise filtering;
- metadata findings (`DataLockFields`, commands, реквизиты, TЧ).

### Итерация 4

- risk scoring;
- MCP tools;
- JSON output для CI и review automation.

## Вывод

`bsl-analyzer` уже находится в той точке зрелости, где задача умного merge-аудита
для 1С реалистична.

Наиболее рациональная стратегия:

- не пытаться строить auto-merge в первой версии;
- сначала сделать сильный merge-review assistant;
- опереться на уже существующие parser/HIR/metadata/search подсистемы;
- двигаться от `.bsl` module audit к object-level audit и только потом к более сложным сценариям.

С практической точки зрения это выглядит как одно из самых естественных направлений роста проекта.
