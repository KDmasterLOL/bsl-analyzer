# Настраиваемый каталог кеша MCP workspace

Статус: утверждено пользователем 2026-08-12.

## Контекст

Профиль `mcp serve --profile workspace` хранит производные данные проекта в
`<source-dir>/.build`: SQLite-базу графа вызовов, поисковый индекс, lease-файлы,
диагностический отчёт о зависании сборки графа и, при включённом логировании,
лог daemon. Каталог создаётся внутри исходной выгрузки конфигурации и может
попасть в обход, загрузку или сравнение сторонних инструментов, которые не
умеют исключать произвольные подкаталоги source root.

Нужен явный CLI-контракт, позволяющий полностью вынести производный кеш за
пределы `source-dir`, не меняя прежнее поведение существующих запусков и не
нарушая совместное использование backend несколькими MCP-клиентами.

## Цели

- Добавить `bsl-analyzer mcp serve --cache-dir <PATH>` для профиля `workspace`.
- Направить в выбранный каталог все производные файлы workspace, которыми
  владеет MCP server.
- Сохранить `<source-dir>/.build` при отсутствии флага.
- Обеспечить одинаковое разрешение пути в broker proxy и daemon.
- Не допустить совместного использования одного backend клиентами с разными
  каталогами кеша.
- Сохранить координацию нескольких поколений daemon через workspace lease.

## Не входит в объём

- Поддержка `--cache-dir` в `mcp install` и генераторах клиентских конфигураций.
- Перенос независимого от workspace кеша справочного профиля из системного
  каталога пользователя.
- Переменная окружения как альтернативный способ задания каталога.
- Миграция или удаление уже существующего `<source-dir>/.build`.
- Изменение форматов SQLite-баз, lease-файлов или broker-протокола.

## CLI-контракт

В `McpServeArgs` добавляется необязательный аргумент:

```text
--cache-dir <PATH>
```

Правила:

1. Аргумент допустим только с `--profile workspace`. Профиль `reference`
   завершает запуск с ошибкой валидации.
2. Если аргумент не указан, эффективный каталог равен
   `<source-dir>/.build`.
3. Относительный путь вычисляется от текущего рабочего каталога процесса, как
   обычный файловый аргумент CLI.
4. Явно заданный каталог создаётся до построения server state и после этого
   канонизируется. Каталог по умолчанию вычисляется от уже канонизированного
   `source-dir`, но сохраняет существующую ленивую семантику создания; если он
   уже существует, его также можно канонизировать. Broker передаёт daemon уже
   абсолютный нормализованный путь.
5. Если явно указанный каталог нельзя создать или канонизировать, запуск
   завершается с ошибкой, содержащей исходный путь и причину. Скрытого отката к
   `<source-dir>/.build` нет.
6. Явный путь, совпадающий с каталогом по умолчанию, эквивалентен отсутствию
   флага и приводит к тому же backend identity.

## Модель каталогов

В `mcp-server::cache` вводится небольшой тип `WorkspaceCacheLayout`. Он является
единственным владельцем соглашения о размещении производных файлов и хранит
нормализованный корневой каталог кеша.

Тип предоставляет методы для получения:

- корня кеша;
- `bsl-graph.db`;
- `bsl-search.db`;
- `writer.lease` и `writer.lease.lock`;
- `bsl-graph-stall-report.txt`;
- `bsl-analyzer-daemon.log`.

Layout не содержит `source-dir`: исходники и производные файлы остаются двумя
разными понятиями. Конструктор CLI-уровня вычисляет layout из `source-dir` и
необязательного `cache-dir`; внутренние подсистемы получают уже готовый layout
и не повторяют правила разрешения пути.

Существующие свободные функции, вычисляющие кеш только из workspace root,
заменяются методами layout либо тонкими совместимыми обёртками только там, где
это необходимо для поэтапного изменения тестов. Производственный код не должен
восстанавливать `.build` самостоятельно.

## Передача данных

### Прямой stdio и HTTP

1. `run_mcp_serve` валидирует профиль и аргументы.
2. CLI вычисляет эффективный `WorkspaceCacheLayout` и заранее подготавливает
   явно заданный каталог.
3. `build_server` передаёт layout в `SharedState::workspace`.
4. `SharedState` передаёт его подсистемам поиска, графа и workspace lease.
5. Фоновые операции используют клон layout или заранее полученные пути.

### Broker и daemon

1. Broker вычисляет канонические `source-dir` и cache root.
2. Cache root включается в `BackendKey` вместе с source dir, профилем, версией,
   embedding fingerprint и topology fingerprint.
3. При запуске дочернего процесса broker добавляет
   `--cache-dir <canonical-path>`.
4. Daemon повторно строит тот же `BackendKey`; переданный абсолютный путь
   исключает зависимость от его рабочего каталога.
5. Только выигравший bind daemon строит `SharedState`, как и сейчас.

Включение cache root в digest даёт следующие гарантии:

- одинаковые source dir и cache dir переиспользуют backend;
- разные cache dir создают разные backend;
- значение по умолчанию и явно заданный `<source-dir>/.build` совпадают;
- lease координирует только процессы, действительно пишущие в один каталог.

## Изменения подсистем

### SharedState и поиск

`SharedState::workspace` принимает layout вместе с `source_dir`. Инициализация
локального search store, фоновые embed/sync операции и проверка persisted mark
sequence получают путь `bsl-search.db` или `bsl-graph.db` из layout.

Reference search продолжает использовать системный пользовательский кеш и не
зависит от нового типа.

### Граф

`GraphState` хранит layout рядом с workspace root. Workspace root по-прежнему
используется для чтения конфигурации и вычисления fingerprint, а layout — только
для открытия, сборки, публикации и snapshot базы графа. Stall report размещается
рядом с graph DB через тот же layout.

### Workspace lease

`WorkspaceLease::claim` принимает cache layout или cache root вместо source
root. Record и lock всегда находятся в эффективном каталоге кеша. Сообщения об
ошибках показывают именно cache root, чтобы диагностика не вводила пользователя
в заблуждение.

### Daemon log

Истинные значения `BSL_MCP_DAEMON_LOG` сохраняют прежнюю семантику, но путь по
умолчанию берётся из layout. Явное файловое значение переменной окружения, как и
раньше, имеет приоритет над каталогом кеша.

## Обработка ошибок

- Ошибка подготовки явно заданного cache dir является ошибкой запуска. Для
  каталога по умолчанию сохраняется существующее поведение его ленивого
  создания подсистемами.
- После успешной подготовки каталог не заменяется запасным путём.
- Ошибки отдельных операций чтения или записи сохраняют существующее поведение
  соответствующей подсистемы и ссылаются на фактический путь.
- Потеря lease остаётся штатным состоянием: устаревший daemon продолжает
  обслуживать опубликованные данные, но прекращает запись.
- Broker fallback на прямой stdio использует тот же уже разрешённый layout и не
  возвращается к `.build`.

## Тестирование

### Unit-тесты cache layout

- отсутствие override даёт `<source-dir>/.build`;
- абсолютный override используется без изменений после канонизации;
- относительный override разрешается от текущего каталога;
- поддерживаются пути с пробелами и кириллицей;
- методы layout возвращают все ожидаемые имена файлов.

### CLI и broker

- `--cache-dir` принимается для workspace и отклоняется для reference;
- cache root является независимой осью `BackendKey`;
- одинаковые эффективные каталоги дают одинаковый digest;
- разные каталоги дают разные digest;
- команда дочернего daemon содержит абсолютный `--cache-dir`;
- broker fallback передаёт тот же layout в прямой server.

### MCP server

- graph DB, search DB и lease создаются во внешнем каталоге;
- daemon log и stall report используют внешний каталог;
- при внешнем cache dir внутри source root не появляется `.build`;
- без флага существующие тесты подтверждают прежнее размещение;
- удалённый cache dir корректно пересоздаётся существующей lease-логикой.

Для тестов, меняющих текущий каталог процесса, следует избегать параллельной
зависимости от process-global cwd. Предпочтительно вынести разрешение пути в
чистую функцию с передаваемым `current_dir`; production-обёртка подставляет
`std::env::current_dir()`.

## Документация

В `docs/mcp/README.md` и примерах ручного `mcp serve` необходимо описать:

- назначение `--cache-dir`;
- значение по умолчанию;
- разрешение относительных путей;
- пример вынесения кеша за пределы source root;
- то, что существующий кеш автоматически не переносится.

## Критерии готовности

Изменение готово, когда:

1. Все режимы workspace (`stdio`, `broker`, `daemon`, `http`) используют один и
   тот же эффективный cache root.
2. Все производные workspace-файлы создаются во внешнем каталоге при заданном
   флаге.
3. Source root остаётся без `.build`, если его не было до запуска.
4. Broker identity различает разные cache dir и переиспользует одинаковые.
5. Запуск без флага полностью сохраняет прежний контракт.
6. Новые и затронутые тесты проходят на Windows и Unix-совместимых путях.
