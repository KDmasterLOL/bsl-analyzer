# Политика версионирования

## Обзор

bsl-analyzer использует подход к версионированию, основанный на дате релиза, с адаптацией под специфику проекта.

## Схема версий

### Внутренние крейты (не публикуются)

Все крейты в `/crates/` используют версию `0.0.0`:

```toml
[package]
name = "parser"
version = "0.0.0"  # Внутренний крейт, версия не важна
```

**Обоснование:**

- Внутренние крейты не публикуются на crates.io
- Нет гарантий стабильности API между коммитами
- Упрощает разработку — не нужно бампить версии при каждом изменении

### Публикуемые библиотеки (будущее)

Если отдельные крейты будут публиковаться на crates.io, они должны следовать [semver](https://semver.org/):

- **MAJOR** — несовместимые изменения API
- **MINOR** — новая функциональность с сохранением совместимости
- **PATCH** — исправления багов

### Релизы bsl-analyzer

Основной продукт (LSP-сервер) версионируется по схеме:

```
YYYY.MM.DD[-suffix]
```

**Примеры:**

- `2025.01.15` — релиз от 15 января 2025
- `2025.01.15-rc1` — релиз-кандидат
- `2025.01.15-beta` — бета-версия

**Обоснование:**

- Простота — дата релиза очевидна
- Нет споров о том, это MAJOR или MINOR изменение
- Дата релиза очевидна без споров о семантическом значении версии

## Ветки и релизы

### Ветки

| Ветка     | Назначение          | Стабильность                   |
| --------- | ------------------- | ------------------------------ |
| `main`    | Основная разработка | Нестабильная, но компилируется |
| `release` | Стабильные релизы   | Стабильная                     |

### Процесс релиза

```
main (разработка)
    │
    ├─── тестирование ───► release (стабильный)
    │                           │
    └─── tag: 2025.01.15 ◄──────┘
```

1. Разработка ведётся в `main`
2. Когда готов релиз — создаётся тег с датой
3. Ветка `release` обновляется до тега
4. Собираются артефакты (бинарники, VSIX)

## Changelog

### Формат

Changelog ведётся в `CHANGELOG.md` в формате [Keep a Changelog](https://keepachangelog.com/):

```markdown
## [2025.01.15]

### Добавлено

- Диагностика EmptyCodeBlock (BSL001)
- Поддержка SDBL запросов

### Изменено

- Улучшена производительность парсера на 20%

### Исправлено

- Падение при парсинге пустых файлов

### Совместимость

- Диагностики: 50/181
```

### Категории

- **Добавлено** — новая функциональность
- **Изменено** — изменения в существующей функциональности
- **Устарело** — функциональность, которая будет удалена
- **Удалено** — удалённая функциональность
- **Исправлено** — исправления багов
- **Безопасность** — исправления уязвимостей
- **Совместимость** — информация о совместимости

## Теги Git

### Формат тегов

```
v2025.01.15        # Релиз
v2025.01.15-rc1    # Релиз-кандидат
v2025.01.15-beta   # Бета
```

### Создание тега

```bash
# Создание аннотированного тега
git tag -a v2025.01.15 -m "Release 2025.01.15"

# Отправка тега
git push origin v2025.01.15
```

## CI/CD и версия

### Определение версии при сборке

Версия определяется автоматически:

1. **Из git тега** — если собирается тег
2. **Из git описания** — `git describe --tags`
3. **Fallback** — `0.0.0-dev`

```rust
// build.rs или xtask
fn version() -> String {
    // Пример: v2025.01.15-5-g1234abc → 2025.01.15-dev.5+g1234abc
    env::var("CFG_RELEASE")
        .or_else(|_| git_describe())
        .unwrap_or_else(|_| "0.0.0-dev".to_string())
}
```

### Артефакты релиза

При создании тега CI собирает:

- `bsl-analyzer-{version}-{platform}.tar.gz` — бинарник
- `bsl-analyzer-{version}.vsix` — расширение VS Code (будущее)

## Фазы разработки

### Текущая фаза: Alpha (0.x)

- Нет гарантий стабильности API
- Версии: `2025.xx.xx-alpha`
- Breaking changes возможны в любой момент

### Будущие фазы

| Фаза   | Критерии                     | Версии             |
| ------ | ---------------------------- | ------------------ |
| Alpha  | Разработка                   | `YYYY.MM.DD-alpha` |
| Beta   | 100+ диагностик, базовый LSP | `YYYY.MM.DD-beta`  |
| RC     | 181 диагностика, полный LSP  | `YYYY.MM.DD-rc1`   |
| Stable | Production ready             | `YYYY.MM.DD`       |

## Зависимости

### Политика обновления

- **Patch-версии** — обновлять свободно
- **Minor-версии** — обновлять после проверки changelog
- **Major-версии** — обновлять с осторожностью, тестировать

### Закрепление версий

Критичные зависимости закрепляются:

```toml
# Cargo.toml
[workspace.dependencies]
rowan = "=0.15.15"      # Закреплено — критичная зависимость
salsa = "0.17"          # Разрешены patch-обновления
logos = "0.14"          # Разрешены patch-обновления
```

## Пример workflow

```bash
# 1. Разработка в main
git checkout main
# ... коммиты ...

# 2. Подготовка релиза
# Обновить CHANGELOG.md
# Проверить cargo test, cargo clippy

# 3. Создание тега
git tag -a v2025.01.15 -m "Release 2025.01.15

- 50 диагностик
- Базовая поддержка LSP"

# 4. Публикация
git push origin v2025.01.15

# 5. CI автоматически собирает артефакты
```
