## Requirements
### Requirement: Версионируемая базовая линия диагностик
Анализатор `MUST` поддерживать хранимую в репозитории базовую линию известных диагностик в детерминированном версионируемом формате. Файл обязан содержать версию схемы, область проекта и упорядоченный набор записей, но не должен содержать абсолютные пути.

#### Scenario: Повторное формирование без изменений
- **WHEN** базовая линия формируется повторно для неизменившегося проекта с теми же настройками анализа
- **THEN** анализатор создаёт побайтово идентичный файл с путями относительно корня проекта и устойчивым порядком записей

#### Scenario: Неподдерживаемая версия схемы
- **WHEN** анализатор читает базовую линию с неподдерживаемой версией схемы
- **THEN** проверка завершается явной ошибкой и не выполняется без учёта базовой линии

#### Scenario: Несовпадающая область проекта
- **WHEN** область проекта в базовой линии не соответствует анализируемому проекту
- **THEN** анализатор завершает проверку явной ошибкой и не сопоставляет записи из другой области, включая случай тех же каталогов с другими именами, порядком или зависимостями расширений

#### Scenario: Корень вне проекта
- **WHEN** при включённой базовой линии основной корень или корень расширения нельзя представить нормализованным путём внутри корня проекта
- **THEN** анализатор сообщает ошибку конфигурации и не записывает абсолютный путь или путь с `..`

### Requirement: Устойчивое сопоставление диагностик
Анализатор `MUST` сопоставлять диагностику с записью базовой линии по единому устойчивому отпечатку, включающему нормализованный относительный путь, код диагностики, нормализованный фрагмент исходной строки и порядковый номер одинакового срабатывания. Номер строки, текст сообщения и уровень важности не должны входить в идентичность записи.

#### Scenario: Сдвиг строк без изменения причины
- **WHEN** над известной диагностикой добавлены или удалены строки, но её путь, код, нормализованный исходный фрагмент и порядковый номер не изменились
- **THEN** диагностика остаётся известной

#### Scenario: Изменение проблемного выражения
- **WHEN** исходный фрагмент известной диагностики изменён
- **THEN** текущее срабатывание классифицируется как новое, а прежняя запись — как исчезнувшая

#### Scenario: Одинаковые срабатывания в одном файле
- **WHEN** один код диагностики несколько раз срабатывает на одинаковом нормализованном фрагменте в одном файле
- **THEN** порядковый номер однозначно различает записи и предотвращает совпадение нескольких диагностик с одной записью

#### Scenario: Единый отпечаток отчёта Code Quality
- **WHEN** одна диагностика представлена базовой линией и отчётом GitLab Code Quality с одинаковым нормализованным входным путём
- **THEN** обе поверхности используют общую реализацию алгоритма устойчивого отпечатка

#### Scenario: Исходный фрагмент недоступен
- **WHEN** команда создания или обновления не может получить исходный фрагмент для текущей диагностики
- **THEN** команда завершается ошибкой до записи, а действующее запасное поведение отдельного отчёта Code Quality не используется для базовой линии

### Requirement: Классификация результата полного анализа
После штатных подавлений анализатор `MUST` разделять результат полного анализа на новые, известные и исчезнувшие диагностики. Новыми являются текущие диагностики без записи, известными — сопоставленные текущие диагностики, исчезнувшими — записи без текущего срабатывания.

#### Scenario: Только известные диагностики
- **WHEN** все текущие диагностики сопоставлены и исчезнувших записей нет
- **THEN** проверка базовой линии завершается успешно и сообщает число известных диагностик

#### Scenario: Появилась новая диагностика
- **WHEN** текущая диагностика не сопоставлена с базовой линией
- **THEN** она остаётся активной, отображается пользователю и приводит к неуспешному коду завершения строгой проверки

#### Scenario: Известная диагностика исчезла
- **WHEN** запись базовой линии не имеет текущего срабатывания в полном анализе
- **THEN** анализатор сообщает её как исчезнувшую и строгая проверка требует явного обновления базовой линии

#### Scenario: Полный снимок не доказан
- **WHEN** обход устарел, отменён, усечён или содержит непрочитанный входной файл
- **THEN** результат не получает состояние полного, не объявляет глобально исчезнувшие записи и не принимается командой изменения базовой линии

#### Scenario: Диагностика подавлена исходным кодом
- **WHEN** срабатывание отключено действующей директивой `bsl-analyzer` в исходном коде
- **THEN** оно не участвует в сопоставлении и не записывается в базовую линию

#### Scenario: Ошибка директивы подавления
- **WHEN** анализатор формирует `UnknownSuppressionCode` или `SuppressionWithoutCode`
- **THEN** эта защитная диагностика остаётся активной и не может быть скрыта базовой линией

### Requirement: Проверка без изменения базовой линии
Обычный анализ и строгая проверка `MUST` читать базовую линию без её изменения. Отсутствующий, повреждённый или несовместимый настроенный файл обязан приводить к явной ошибке, а не к неявному запуску без базовой линии.

#### Scenario: Базовая линия не настроена
- **WHEN** раздел `[diagnostics.baseline]` отсутствует
- **THEN** анализатор не читает файл базовой линии, сохраняет прежние диагностики и код завершения и сообщает состояние `disabled` в поверхностях со сводкой

#### Scenario: Обычный анализ проекта
- **WHEN** пользователь запускает анализ с настроенной корректной базовой линией
- **THEN** файл базовой линии не изменяется, известные диагностики исключаются из активных результатов, а новые остаются видимыми

#### Scenario: Настроенный файл отсутствует
- **WHEN** в конфигурации указан отсутствующий файл базовой линии
- **THEN** анализ завершается ошибкой конфигурации и не выдаёт результат, ошибочно представленный как проверенный по базовой линии

#### Scenario: Путь выходит из проекта
- **WHEN** настроенный путь после разрешения выходит из канонического корня проекта или существующая цель является символической ссылкой
- **THEN** анализатор сообщает ошибку конфигурации и не читает и не заменяет целевой файл

#### Scenario: Повреждённый файл
- **WHEN** файл базовой линии не соответствует схеме или содержит неоднозначные дубликаты
- **THEN** анализатор сообщает проверяемую причину ошибки и не изменяет файл

### Requirement: Только явное атомарное изменение
Анализатор `MUST` создавать и обновлять базовую линию только отдельными явными командами. Изменение обязано выполняться атомарно, а результат — сообщать количества добавленных, удалённых и неизменившихся записей.

#### Scenario: Первичное создание
- **WHEN** пользователь настроил путь, целевой файл отсутствует и пользователь явно создаёт базовую линию по результату полного анализа
- **THEN** анализатор атомарно записывает все допустимые текущие диагностики и сообщает число и состав созданных записей

#### Scenario: Создание без настроенного пути
- **WHEN** пользователь запускает `create` без `[diagnostics.baseline].path`
- **THEN** команда завершается явной ошибкой до анализа и записи

#### Scenario: Явное обновление
- **WHEN** пользователь явно обновляет существующую базовую линию по результату полного анализа
- **THEN** анализатор атомарно добавляет новые, удаляет исчезнувшие, сохраняет идентичность известных записей, освежает их информационные поля и сообщает итоговые количества

#### Scenario: Сбой записи
- **WHEN** запись нового содержимого или его замена завершается ошибкой
- **THEN** прежний файл остаётся пригодным для чтения и анализатор возвращает неуспешный результат

#### Scenario: Попытка неявного роста
- **WHEN** `diagnostics baseline check` обнаруживает новые диагностики
- **THEN** команда не добавляет их в базовую линию и завершается неуспешно, а обычный `analyze` сохраняет прежний контракт кода завершения

### Requirement: Защита от неполного обновления
Команды создания и обновления `MUST` принимать результат только полного анализа области проекта. Анализ с `analysis.diff_base`, фильтром авторов, выбором отдельных файлов или иной неполной областью не должен перезаписывать базовую линию.

#### Scenario: Обновление при включённом diff_base
- **WHEN** пользователь запускает изменение базовой линии при настроенном `analysis.diff_base`
- **THEN** анализатор отказывает до записи и объясняет, что требуется полный анализ

#### Scenario: Чтение при частичном анализе
- **WHEN** интерактивная поверхность анализирует только часть проекта
- **THEN** текущие диагностики этой части могут быть классифицированы, но записи вне доказанно проанализированной области не объявляются исчезнувшими

#### Scenario: Ограниченный или отменённый запрос MCP
- **WHEN** актуальный запрос рабочей области ограничен числом файлов или отменён после завершения части целых файлов
- **THEN** MCP помечает состояние базовой линии как частичное и считает исчезнувшими только записи внутри доказанно завершённых целых файлов

#### Scenario: Устаревший снимок MCP
- **WHEN** запрос обслужен устаревшим снимком либо во время незавершённой или неуспешной перезагрузки
- **THEN** MCP помечает состояние как частичное, не считает ни один файл доказанно завершённым и возвращает `resolved = 0`

### Requirement: Единое поведение CLI, MCP и LSP
CLI, MCP и LSP `MUST` использовать один общий механизм загрузки, проверки и сопоставления базовой линии. CLI и MCP обязаны возвращать состояние базовой линии, а LSP — применять ту же классификацию, показывать новые диагностики как активные и явно сообщать ошибку загрузки без отдельной реализации отпечатков.

#### Scenario: Одинаковый проект в трёх поверхностях
- **WHEN** CLI, MCP и LSP анализируют одну ревизию проекта с одной конфигурацией базовой линии
- **THEN** они одинаково классифицируют каждую текущую диагностику как новую или известную

#### Scenario: Ответ MCP
- **WHEN** клиент запрашивает диагностики файла или рабочей области через MCP с корректной базовой линией
- **THEN** ответ содержит активные новые диагностики и сводные количества новых, известных и доказанно исчезнувших записей

#### Scenario: Ошибка базовой линии в MCP
- **WHEN** клиент запрашивает диагностики через MCP с отсутствующей, повреждённой или неподдерживаемой базовой линией
- **THEN** обычный структурированный ответ использует ошибочную ветвь схемы с `baseline.state = "error"`, кодом и деталью, без находок и классификационных счётчиков

#### Scenario: Публикация LSP
- **WHEN** LSP публикует диагностики документа при действующей базовой линии
- **THEN** известные диагностики не публикуются как активные, новые публикуются, а ошибка чтения базовой линии явно доводится до клиента

#### Scenario: Ошибка базовой линии в LSP
- **WHEN** настроенный файл отсутствует, повреждён или имеет неподдерживаемую схему
- **THEN** LSP публикует все текущие диагностики без фильтрации базовой линией и один раз сообщает ошибку для текущего файлового отпечатка

#### Scenario: Изменение файла в резидентной поверхности
- **WHEN** файл базовой линии изменён, атомарно заменён или удалён во время работы MCP или LSP
- **THEN** поверхность перечитывает только снимок базовой линии, повторно формирует ответ или публикацию и не пересоздаёт семантическую базу проекта

#### Scenario: Совместимость отчёта Code Quality
- **WHEN** обычный анализ формирует отчёт GitLab Code Quality при включённой базовой линии
- **THEN** отчёт остаётся корневым JSON-массивом активных замечаний с прежними отпечатками и не содержит фиктивного элемента сводки

### Requirement: Независимость механизмов baseline
Базовая линия диагностик `MUST` иметь отдельную конфигурацию и семантику и не должна подменять `[analysis].diff_base`, `search.baseline`, правила диагностики или директивы подавления в исходном коде.

#### Scenario: Одновременно настроен search.baseline
- **WHEN** проект использует базовую линию диагностик и `search.baseline`
- **THEN** каждый механизм читает собственный файл и влияет только на свою подсистему

#### Scenario: Правило отключено конфигурацией
- **WHEN** правило отключено в `[diagnostics.parameters]`
- **THEN** его срабатывания не создаются и не попадают в базовую линию
