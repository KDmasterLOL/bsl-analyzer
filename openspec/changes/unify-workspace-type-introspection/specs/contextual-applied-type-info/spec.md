## ADDED Requirements

### Requirement: Раздельные карточки прикладных граней
`symbol_info` MUST распознавать `СправочникОбъект.<Имя>`, `СправочникСсылка.<Имя>`, `СправочникМенеджер.<Имя>` и `ОбработкаОбъект.<Имя>`, отклонять неизвестную грань или объект и MUST NOT смешивать их члены.

#### Scenario: Объектная грань справочника
- **WHEN** запрошен `СправочникОбъект.Контрагенты`
- **THEN** карточка содержит объектные члены и не содержит членов только ссылки или менеджера

#### Scenario: Ссылочная грань справочника
- **WHEN** запрошен `СправочникСсылка.Контрагенты`
- **THEN** карточка содержит читаемые реквизиты и платформенный интерфейс ссылки, но не экспорт модуля объекта

#### Scenario: Менеджерская грань справочника
- **WHEN** запрошен `СправочникМенеджер.Контрагенты`
- **THEN** карточка содержит свойства, экспорт модуля менеджера и платформенный интерфейс менеджера

#### Scenario: Объектная грань обработки
- **WHEN** запрошен `ОбработкаОбъект.УниверсальныйОбменДаннымиXML`
- **THEN** карточка содержит реквизиты и экспорт объектного модуля обработки

#### Scenario: Неизвестная грань
- **WHEN** имя содержит неизвестную грань или объект
- **THEN** сервер возвращает версионированный `not_found` с исходным именем

### Requirement: Единое перечисление и точное разрешение членов
Один сборщик карточки MUST обслуживать полный перечень и точное разрешение. Для объектной грани он SHALL объединять прикладные и стандартные реквизиты, экспортные методы и переменные объектного модуля и платформенный интерфейс; для ссылочной — читаемые реквизиты и платформенный интерфейс; для менеджерской — свойства, экспортные методы и переменные модуля менеджера и платформенный интерфейс. Отсутствующий или непрочитанный модуль MUST NOT скрывать остальные категории. Точный запрос MUST возвращать всех одноимённых кандидатов, а не первый по порядку источников.

#### Scenario: Реквизит и экспортный метод объекта
- **WHEN** справочник имеет реквизит `ИНН` и экспортный метод объектного модуля
- **THEN** объектная карточка содержит оба с разным происхождением

#### Scenario: Экспортная переменная объекта
- **WHEN** объектный модуль объявляет `Перем мСчетчик Экспорт`
- **THEN** карточка содержит свойство `module`, а `field_lookup` не создаёт `UnresolvedField`

#### Scenario: Экспортная переменная менеджера
- **WHEN** модуль менеджера объявляет экспортную переменную
- **THEN** менеджерская карточка и `field_lookup` используют один effective module и разрешают поле без полного сканирования индекса

#### Scenario: Модуль отсутствует или не читается
- **WHEN** соответствующий модуль отсутствует либо не был загружен
- **THEN** карточка возвращает метаданные и платформу без вымышленных экспортных членов

#### Scenario: Одно имя в нескольких источниках
- **WHEN** реквизит, экспортный и платформенный член имеют одинаковое имя
- **THEN** точный запрос возвращает всех кандидатов с происхождением

### Requirement: Структура, происхождение и тип члена
Каждый член MUST содержать имя, вид, совместимое строковое отображение типа либо сигнатуру, структурированные варианты типа, происхождение `metadata|module|platform`, необязательный `source_extension` и доступность. Разные источники MUST NOT схлопываться с потерей происхождения.

#### Scenario: Составной статический тип
- **WHEN** реквизит имеет два варианта составного типа
- **THEN** карточка сохраняет оба структурированных технических имени и строковое отображение для старого клиента

#### Scenario: Одинаковые представления статических типов
- **WHEN** два статических варианта имеют одинаковое представление
- **THEN** они остаются разными по `technical_name`

### Requirement: Техническая идентичность живого варианта
Новый ответ `СтруктураМетаданныхPOST` MUST сохранять прежнее поле `type` и добавлять `typeVariants`, где каждый элемент содержит `technicalName` и `presentation`. В `metadata(action="object", mode="infobase")` это MUST сериализоваться как `type_variants`, где каждый вариант имеет `presentation`, nullable `technical_name`, `resolution` и причину для `unresolved`. Для нового сервиса `technicalName` MUST быть получено из машинной идентичности типа 1С; старое строковое представление MUST NOT сопоставляться с локальным деревом рабочей области. Неизвестные добавочные поля ответа сервиса MUST игнорироваться.

#### Scenario: Новый сервис возвращает составной тип
- **WHEN** живой реквизит допускает несколько технических типов
- **THEN** новый бинарник возвращает каждый вариант с отдельным каноническим `technical_name` и `resolution="source"`

#### Scenario: Одинаковые представления живых типов
- **WHEN** два варианта имеют одинаковый `presentation`
- **THEN** сервер сохраняет два разных технических имени

#### Scenario: Ответ старого сервиса
- **WHEN** сервис передал только прежнюю строку `type`
- **THEN** новый бинарник возвращает `technical_name=null`, `resolution="unresolved"` и причину отсутствия машинной идентичности

#### Scenario: Другая информационная база
- **WHEN** живая connection не соответствует загруженной рабочей области
- **THEN** сервер не использует локальное дерево для уверенного сопоставления строкового представления

#### Scenario: Старый бинарник с новым сервисом
- **WHEN** старый бинарник читает ответ нового сервиса
- **THEN** сохранённое поле `type` остаётся доступно, а добавочные поля не требуют отката сервиса

### Requirement: Контекст позиции дополняет именованную цель
Без `symbol` существующая пара `path` + `line` с необязательными `root_id` и `column` MUST сохранять позиционный поиск. С `symbol` имя MUST задавать цель, а такая же необязательная позиция SHALL задавать контекст доступности. `path` без `line`, а также `line`, `column` или `root_id` без `path` MUST отклоняться. Без позиции сервер MUST возвращать все известные члены с декларативными ограничениями.

#### Scenario: Именованный тип в серверном контексте
- **WHEN** переданы `symbol`, `path` и `line` серверного модуля с необязательными `root_id` и `column`
- **THEN** серверные и клиентские ограничения членов отмечены относительно этой позиции

#### Scenario: Именованный тип без позиции
- **WHEN** передан только `symbol`
- **THEN** возвращены все известные члены без скрытого выбора контекста

#### Scenario: Старый позиционный запрос
- **WHEN** переданы только `path` и `line`, с необязательными `root_id` и `column`
- **THEN** выполняется прежний поиск символа в позиции

#### Scenario: Неполная позиция
- **WHEN** вместе с `symbol` передан `path` без `line` либо `line`, `column` или `root_id` без `path`
- **THEN** сервер возвращает опубликованную ошибку проверки входа

### Requirement: Происхождение членов расширений
Карточка MUST вычислять effective members из уже загруженных root в объявленном топологическом порядке и сохранять имя расширения, добавившего либо заменившего член. Позиционный запрос SHALL учитывать видимость root файла; именованный запрос без позиции SHALL использовать результирующее designer-представление across-roots. Повторное чтение XML MUST NOT выполняться.

#### Scenario: Уникальный реквизит расширения
- **WHEN** расширение добавляет новый реквизит
- **THEN** карточка содержит его `source_extension`

#### Scenario: Замена одноимённого члена
- **WHEN** расширение заменяет базовый одноимённый член
- **THEN** effective member имеет источник победившего расширения, а базовый не выдаётся как действующий

#### Scenario: Два расширения
- **WHEN** два расширения меняют один член
- **THEN** победитель и источник определяются тем же устойчивым топологическим приоритетом, что остальной анализ

#### Scenario: Effective module расширения
- **WHEN** расширение заменяет объектный или менеджерский модуль
- **THEN** карточка и `field_lookup` используют экспорт победившего effective module

### Requirement: Контекстная карточка формы
`symbol_info` MUST обогащать управляемую форму реквизитами, элементами, экспортными методами модуля формы и применимым платформенным интерфейсом. Тип `DataPath` SHALL выводиться существующими `form_element_type` и загруженными метаданными. Полный и точный запрос MUST использовать единый сборщик и возвращать кандидатов при совпадении имени реквизита, элемента, экспортного или платформенного члена. Обычная форма MUST сохранять прежнюю карточку. После проверки кандидатов управляемой формы точное разрешение MUST сохранять прежний fallback к локальному методу модуля, включая неэкспортный.

#### Scenario: Управляемая форма объекта
- **WHEN** запрошена управляемая форма объекта
- **THEN** карточка содержит реквизиты, элементы, экспортные методы и применимый платформенный интерфейс с происхождением

#### Scenario: Тип элемента через DataPath
- **WHEN** элемент связан с `Объект.ИНН`
- **THEN** его тип выведен через основное значение формы и метаданные без повторного чтения XML

#### Scenario: Одноимённые члены формы
- **WHEN** реквизит, элемент и экспортный метод имеют одно имя
- **THEN** точный запрос возвращает кандидатов, а не первый найденный член

#### Scenario: Обычная форма не меняется
- **WHEN** старый клиент повторяет запрос карточки обычной формы
- **THEN** ответ не получает новое платформенное объединение и сохраняет прежнее разрешение

#### Scenario: Закрытый helper управляемой формы
- **WHEN** старый клиент запрашивает по прежнему квалифицированному имени неэкспортный локальный метод модуля управляемой формы
- **THEN** точное разрешение по-прежнему возвращает этот метод после отсутствия кандидата общего сборщика

### Requirement: Версионированный и совместимый symbol_info
`symbol_info` MUST публиковать `outputSchema` целого инструмента и `schema_version` каждого успешного структурированного варианта. Старые запросы без фильтров и прежние значения `include=definition|type|doc` MUST сохранять семантику; члены не MUST становиться скрыто зависимыми от `include`. Необязательный `member_kind` SHALL принимать `attribute`, `tabular_section`, `method`, `variable`, `property`, `form_attribute`, `form_element`, `handler`, а `member_name` — точное регистронезависимое имя; оба фильтра SHALL сужать только членов. Успешный, `not_found`, неоднозначный и усечённый варианты MUST соответствовать опубликованной схеме; ошибки входа и внутренние ошибки MUST проверяться отдельно как ошибки MCP.

#### Scenario: Старый include-запрос
- **WHEN** клиент повторяет прежний запрос с `include=["type"]` без новых фильтров
- **THEN** прежние секции и наличие членов не меняются из-за новой трактовки `include`

#### Scenario: Фильтр точного члена
- **WHEN** клиент задаёт `member_kind` и `member_name`
- **THEN** сервер возвращает только совпадающих членов и сохраняет кандидатов разных источников

### Requirement: Единый диагностируемый бюджет карточки
После устойчивой сортировки по категории, имени, происхождению и расширению `max_output_tokens` MUST применяться к одному сериализованному `CallToolResult`, включая текст, `structuredContent`, документ, фрагмент, членов и usages. Усечение MUST возвращать единые `truncated`/`budget_hint` и фильтры `member_kind`/`member_name`. Только обязательный минимальный конверт без предметного элемента MAY превысить слишком малый бюджет и MUST отметить исключение.

#### Scenario: Большая карточка усечена
- **WHEN** полная карточка не помещается в бюджет
- **THEN** ответ содержит устойчивый префикс, единый признак и способ запросить конкретный вид или имя

#### Scenario: Полный wire-ответ проверен
- **WHEN** сериализуются большая карточка и минимальный бюджет
- **THEN** измеряется весь `CallToolResult`, а не независимо его секции или только текст
