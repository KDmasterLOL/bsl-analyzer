## Why

Крупные существующие конфигурации могут содержать сотни подтверждённых диагностик, из-за чего строгий шлюз «ноль замечаний» невозможно включить сразу. Текущие обходы — отключение правила, подавления в исходном коде или анализ только изменённых строк — либо скрывают будущие дефекты, либо изменяют проверяемый код и не дают полного сравнения результата анализа.

## What Changes

- Добавляется версионируемая базовая линия диагностик, фиксирующая только известные срабатывания по устойчивым отпечаткам.
- Обычная проверка полного проекта показывает новые диагностики, отдельно сообщает исчезнувшие записи и не изменяет базовую линию.
- Обновление базовой линии выполняется только явной командой и не допускает неявного роста в проверочном режиме.
- Один и тот же классификатор применяется в CLI, MCP и LSP после штатных подавлений диагностик; CLI и MCP возвращают сводку состояния, а LSP публикует только активные диагностики и явно сообщает ошибку загрузки.
- Формат использует общий устойчивый отпечаток, переиспользуемый репортёром GitLab Code Quality, и учитывает версию схемы и область проекта.
- Базовая линия диагностик остаётся независимой от `[analysis].diff_base` и от `search.baseline`.

## Capabilities

### New Capabilities

- `diagnostics-baseline`: создание, проверка, явное обновление и применение версионируемой базовой линии известных диагностик во всех поверхностях анализатора.

### Modified Capabilities

Нет.

## Impact

- Общий конвейер `ide-diagnostics`, конфигурация проекта и модель устойчивого отпечатка диагностик.
- CLI-команды и коды завершения для создания, проверки и обновления базовой линии.
- MCP `diagnostics` возвращает состояние и счётчики, а LSP-публикация использует ту же классификацию без нового протокольного расширения.
- Репортёры CLI, прежде всего Code Quality, должны использовать общий алгоритм отпечатка без изменения существующей устойчивости к сдвигу строк.
- Документация конфигурации, CI и миграции проектов с существующим долгом.
