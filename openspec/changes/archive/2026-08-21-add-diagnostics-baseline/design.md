## Context

Сейчас анализатор умеет отключать правила настройками, подавлять отдельные срабатывания директивами в BSL и ограничивать вывод через `[analysis].diff_base` и `ignored_authors`. Эти механизмы меняют состав анализа или исходный код, но не решают задачу постепенного погашения существующего долга: полный проект должен проверяться, известные срабатывания не должны мешать, а новые и исчезнувшие — должны требовать решения.

CLI `analyze`, резидентный MCP и LSP используют общий расчёт диагностик, но по-разному формируют конечный ответ. Устойчивый к сдвигу строк отпечаток уже реализован репортёром GitLab Code Quality как BLAKE3 от относительного пути, кода, нормализованной исходной строки и номера одинакового срабатывания. Его следует поднять в общий слой, а не вводить второй алгоритм.

Базовая линия должна работать после штатных настроек правил и подавлений. Для определения исчезнувших записей необходим полный снимок проекта; результат анализа одного файла или diff-области для этого недостаточен.

## Goals / Non-Goals

**Goals:**

- ввести один переносимый и детерминированный формат базовой линии;
- не скрывать новые диагностики и не допускать неявного роста файла;
- одинаково классифицировать диагностики в CLI, MCP и LSP;
- переиспользовать существующий отпечаток Code Quality;
- безопасно создавать и обновлять файл только по полному анализу;
- дать CI строгий код завершения для новых и исчезнувших записей.

**Non-Goals:**

- замена директив подавления, настройки правил, `analysis.diff_base` или `search.baseline`;
- автоматическое исправление диагностик;
- эвристическое сопоставление после переименования файла или изменения проблемной строки;
- изменение базовой линии из MCP или LSP;
- постоянный кэш результатов анализа CLI; это отдельная задача от хранения известных срабатываний.

## Decisions

### 1. Общий модуль базовой линии в `ide`

Чистые типы схемы, разбор и сериализация байтов, вычисление отпечатка и классификация размещаются в публичном модуле крейта `ide`. Он уже доступен CLI, MCP и LSP и владеет публичным представлением диагностик. Хосты передают в модуль нормализованный относительный путь, исходную строку и диагностику, а получают классифицированный результат и сводку.

Границы ответственности остаются существующими: `project-model` извлекает типизированный раздел базовой линии из сырого `[diagnostics]`, хранит фактическое происхождение конфигурации и разрешает путь и область; CLI владеет полным запуском и атомарной записью; MCP и LSP владеют кэшем, наблюдением и ответами. `ide` не читает файловую систему и не наблюдает за ней.

Репортёр Code Quality переводится на тот же публичный вычислитель отпечатка. Отдельный крейт не создаётся: единственная модель и один алгоритм не оправдывают новую границу пакета.

Альтернатива — оставить сопоставление в CLI и повторить его в MCP/LSP. Она отвергнута из-за неизбежного расхождения семантики и отпечатков.

### 2. JSON-файл со схемой версии 1

Файл содержит:

- `schema_version`;
- `scope`: нормализованный корень источников и упорядоченная топология расширений `{name, path, depends_on}` относительно канонического корня проекта;
- отсортированный массив `diagnostics`;
- для каждой записи: `fingerprint`, относительный путь, код, нормализованный фрагмент и номер одинакового срабатывания;
- информационные поля сообщения, важности и последнего диапазона, которые помогают ревью, но не участвуют в совпадении.

При `update` известная идентичность считается неизменившейся для сводки, но её информационные поля освежаются из текущего полного анализа. Поэтому диапазон и текст не остаются устаревшими после явного обновления и при этом не превращаются в добавление или удаление записи.

Записи сортируются по пути, коду, фрагменту и номеру. JSON записывается с фиксированным форматированием и завершающим переводом строки. Пути используют `/`, не содержат пустых сегментов, `.` или `..`; корень источников и каждый корень расширения должны находиться внутри канонического корня проекта, иначе включение базовой линии является ошибкой конфигурации. Абсолютные пути, время формирования и версия исполняемого файла не сохраняются, чтобы одинаковый проект давал одинаковые байты на разных машинах.

При чтении анализатор пересчитывает `fingerprint` из идентифицирующих полей и отвергает несовпадение, коллизию нормализованных путей, дубликат и запись защитной диагностики. Это не позволяет вручную расширить область подавления, изменив только сохранённый хэш.

Версия схемы отделена от версии анализатора. Изменение рецепта отпечатка требует новой версии схемы и явной миграции.

Альтернативы:

- TOML удобнее редактировать руками, но базовая линия является машинным снимком, а JSON уже используется отчётами и проще строго проверяется через `serde`;
- хранение только хэшей компактнее, но делает ревью и диагностику устаревших записей непрозрачными.

### 3. Сопоставление по существующему отпечатку Code Quality

Общий модуль владеет рецептом хэша, но не выбирает корень пути. Базовая линия всегда передаёт путь относительно канонического корня проекта; Code Quality сохраняет действующий путь, который CLI вычисляет относительно `--workspace-dir`. Поэтому паритет двух поверхностей гарантирован при одинаковом нормализованном входном пути, а существующие золотые отпечатки Code Quality сохраняются для его штатного корня.

Отпечаток версии 1 сохраняет точный действующий рецепт Code Quality без дополнительного префикса: BLAKE3 от четырёх разделённых нулевым байтом частей, причём номер кодируется как `u32` little-endian:

1. нормализованный входной путь, выбранный вызывающей поверхностью: для базовой линии — относительно канонического корня проекта, для Code Quality — действующий путь относительно `--workspace-dir`;
2. код диагностики;
3. исходная строка после свёртки пробельных символов;
4. порядковый номер среди записей с теми же путём, кодом и фрагментом.

Номер строки, диапазон, текст сообщения и важность не входят в идентичность. Поэтому вставка строк выше не создаёт ложную новую диагностику, а изменение проблемного выражения создаёт пару «новая + исчезнувшая». Переименование файла также осознанно создаёт такую пару: автоматическое угадывание перемещений сделало бы подавление неоднозначным.

Нельзя использовать действующий запасной отпечаток Code Quality без исходного фрагмента при записи базовой линии. Если исходную строку получить нельзя, явная команда изменения завершается ошибкой. Это не позволяет создать слишком широкий ключ `path + code + occurrence`.

Сам репортёр Code Quality сохраняет действующее запасное поведение для старых производителей, которые не передают фрагменты: изменение его публичного формата и прежних отпечатков не входит в этот change. Строгий запрет относится только к `create` и `update`.

### 4. Базовая линия применяется после правил и штатных подавлений

Входом классификатора является итог `ide` после настроек `[diagnostics.parameters]` и директив подавления. Поэтому отключённые и штатно подавленные срабатывания не попадают в файл.

Защитные диагностики `UnknownSuppressionCode` и `SuppressionWithoutCode` исключаются из допустимых записей базовой линии и всегда остаются активными. Иначе опечатка в механизме подавления могла бы навсегда скрыться вторым механизмом подавления.

### 5. Полный и частичный режимы имеют разную доказательную силу

Классификатор принимает явный режим области:

- `Full` — разрешает вычислять новые, известные и исчезнувшие записи;
- `Partial` с набором доказанно проанализированных файлов — разрешает классифицировать текущие срабатывания, но определяет исчезнувшие записи только внутри этой области;
- результат одного открытого документа в LSP не используется для глобального вывода об исчезнувших записях.

Классификатор получает `CoverageProof` с общим и проанализированным числом файлов, завершёнными целыми файлами и признаками ошибок. `Full` допустим только при `analyzed == total` и отсутствии `failed`, `unreadable`, `cancelled`, `truncated`, `out_of_scope`, `stale` и незавершённой либо неуспешной перезагрузки. Иначе результат имеет состояние `Partial`, а `create`, `update`, `check` и любой строгий вывод об исчезнувших записях завершаются ошибкой. В актуальном частичном результате исчезновение допустимо только внутри полностью завершённых целых файлов; diff строк, диапазон, код, важность и фильтры представления не доказывают исчезновение. Для устаревшего снимка и незавершённой либо неуспешной перезагрузки множество доказанно завершённых файлов пусто и `resolved = 0`.

Команды записи принимают только `Full`. CLI отказывает в изменении файла при `--incremental`, `--changed-files`, `--git-diff`, `--diff-filter`, `--only-diagnostic`, `[analysis].diff_base`, `ignored_authors` или ином фильтре результата. Это проверяется до открытия файла на запись.

Обычный `analyze` может применять базовую линию совместно с областью вывода, но не изменяет её. Классификация выполняется после настроек правил и директив подавления, но до фильтров представления: кода, важности, диапазона, авторов, diff, числа элементов и бюджета ответа. Сводка относится ко всей доказанно проанализированной области; интерактивные и отфильтрованные запросы маркируются как частичные.

Альтернатива — молча удалять все записи, которых нет в текущем результате. Она отвергнута как путь к потере базовой линии при случайном частичном запуске.

### 6. Конфигурация и команды

Проектная конфигурация получает необязательный раздел:

```toml
[diagnostics.baseline]
path = ".bsl-analyzer-diagnostics-baseline.json"
```

Путь разрешается относительно фактического файла конфигурации и после нормализации должен указывать внутрь канонического корня проекта. Существующая цель не может быть символической ссылкой, а каталог новой цели также должен канонически находиться внутри проекта; это не позволяет конфигурации читать или заменять произвольный файл вне репозитория. `create` требует настроенного раздела и разрешает отсутствие цели; все читающие операции и `update` считают отсутствие, повреждение или неподдерживаемую схему ошибкой. Поэтому первичная миграция начинается с добавления раздела конфигурации, затем выполняется `create`.

CLI получает группу команд:

```text
bsl-analyzer-app diagnostics baseline create --source-dir <path> [--config <path>]
bsl-analyzer-app diagnostics baseline check  --source-dir <path> [--config <path>]
bsl-analyzer-app diagnostics baseline update --source-dir <path> [--config <path>]
```

`create` требует отсутствия целевого файла, `update` — существования корректного файла, `check` ничего не пишет. `create` и `update` сначала полностью вычисляют и проверяют новое содержимое, записывают `tempfile` в том же каталоге, выполняют `flush` и `sync_all`. `create` атомарно публикует готовый inode через `std::fs::hard_link`, который не перезаписывает существующее имя; файловая система без поддержки жёстких ссылок получает явную ошибку без запасной неатомарной записи. `update` использует платформенно корректный `tempfile::persist` с заменой. Временная ссылка удаляется после успеха и при ошибке; конкурентный `create` не перезаписывает победившую цель, а неуспешный `update` сохраняет прежние байты. Контракт гарантирует атомарную видимость целого файла, но не обещает устойчивость записи каталога к потере питания.

Обычный `analyze` автоматически читает настроенную базовую линию и передаёт репортёрам только активные диагностики, добавляя сводку в машинные форматы. Строгий код завершения принадлежит `diagnostics baseline check`; существующий контракт кода завершения `analyze` не меняется скрыто.

MCP и LSP являются только читающими поверхностями. Изменение файла остаётся явным локальным действием CLI, пригодным для ревью в системе контроля версий.

### 7. Единая модель состояния в ответах

Общая сводка содержит:

- состояние: `disabled`, `full`, `partial` или `error`;
- количества `new`, `known`, `resolved`;
- путь базовой линии относительно проекта;
- версию схемы;
- признак полноты результата.

Носитель сводки зависит от существующего формата:

- консоль печатает отдельную строку сводки;
- JSON добавляет поле в существующий объект верхнего уровня;
- JSONL добавляет необязательное поле `baseline` в завершающее событие `done`;
- SARIF хранит сводку в `run.properties`, не используя `baselineState` для частичного результата;
- JUnit хранит сводку в свойствах набора тестов;
- GitLab Code Quality остаётся требуемым GitLab массивом активных замечаний без служебного элемента и без отдельного сопутствующего файла.

MCP повышает версию схемы `diagnostics`, обновляет опубликованный `outputSchema` и добавляет сводку вне урезаемых коллекций; текстовый ответ зеркалит обязательные значения структурированного ответа при любом бюджете. Успешная и ошибочная формы являются двумя ветвями `oneOf`: ошибка базовой линии возвращается существующим внутриполосным структурированным ответом с `baseline.state = "error"`, кодом и деталью, без коллекции находок и без классификационных счётчиков. Активные коллекции успешной формы содержат только новые и небазируемые защитные диагностики. LSP не получает нового протокольного расширения: он публикует только активные диагностики. При ошибке загрузки CLI завершается ошибкой, MCP возвращает описанную ошибочную ветвь, а LSP публикует все текущие диагностики без фильтрации базовой линией и показывает ошибку один раз для файлового отпечатка. Изменение файла разрешает повторную загрузку. Известные записи не превращаются в фиктивные LSP-диагностики.

### 8. Перезагрузка в резидентных процессах

MCP и LSP добавляют целевой файл к существующей инфраструктуре наблюдения за проектом, но ведут его файловый отпечаток и эпоху отдельно от отпечатка конфигурации и топологии. Изменение, атомарная замена или удаление файла сбрасывают только загруженный снимок базовой линии и инициируют повторную публикацию диагностик; семантическая база Salsa и индекс проекта не пересоздаются. Эпоха или отпечаток базовой линии входит в `result_id` ответов MCP для файла и рабочей области, поэтому изменение активного набора никогда не сохраняет прежний идентификатор результата при неизменном поколении Salsa. Таким образом, базовая линия не становится вторым кэшем анализа.

Ошибочный файл кэшируется вместе с его файловым отпечатком, чтобы не перечитывать его на каждый запрос; изменение отпечатка разрешает повторную загрузку.

### 9. Эксплуатационные ограничения

Загрузка и классификация линейны по числу записей и держат один разобранный снимок и одну карту отпечатков на проект; отдельный индекс, фоновый процесс и постоянный кэш не добавляются. Базовая линия отключена по умолчанию, поэтому без раздела конфигурации нет дополнительного ввода-вывода или памяти. Проверка путей и строгий разбор закрывают локальную границу доверия файла из репозитория; сетевых прав и секретов change не вводит. Масштабирование и денежная стоимость неприменимы: работа выполняется в существующем процессе на одном проекте. Эксплуатационный откат описан удалением раздела конфигурации.

## Risks / Trade-offs

- [Одинаковая исходная строка вставлена перед известными копиями] → порядковые номера последующих копий изменятся и дадут явные новые/исчезнувшие записи; это безопаснее неоднозначного подавления.
- [Переименование файла создаёт шум] → пользователь выполняет явное `update` после проверки пары «новая + исчезнувшая»; эвристика переименований не вводится.
- [Старый клиент MCP не знает новых полей] → поля добавляются без удаления существующих коллекций и счётчиков.
- [Большая базовая линия увеличивает память] → файл читается один раз в карту отпечатков; повторный индекс исходников не создаётся.
- [Одновременное обновление двумя процессами] → атомарная замена предотвращает повреждение, но последний успешный писатель победит; конфликт предотвращается обычным контролем версий.
- [Ошибка в рецепте отпечатка скрывает диагностику] → золотые тесты общего алгоритма и проверка паритета Code Quality, CLI, MCP и LSP.
- [Частичный контур ошибочно сообщает resolved] → полнота является обязательным параметром классификации и отдельным полем ответа; запись разрешена только для `Full`.
- [Непрочитанный файл или усечённый MCP-обход выдаёт ложный `resolved`] → такой снимок всегда `Partial`/`error`; глобальные исчезнувшие записи вычисляются только при полном актуальном обходе.
- [Формат Code Quality ломается из-за служебной сводки] → его корневой JSON-массив остаётся без метаданных; сводка доступна через консоль, строгий код завершения и другие машинные форматы.

## Migration Plan

1. Добавить общий формат и классификатор без включения базовой линии по умолчанию.
2. Перевести Code Quality на общий отпечаток и доказать неизменность существующих золотых значений.
3. Добавить конфигурацию и CLI-команды, затем читающую интеграцию CLI.
4. Подключить тот же снимок к MCP и LSP и проверить перезагрузку файла.
5. Обновить документацию: проект сначала добавляет раздел конфигурации, явно выполняет `create`, ревьюит файл и включает `check` в CI.

Откат состоит в удалении раздела `[diagnostics.baseline]`; без него поведение анализа остаётся прежним. Формат не обновляется автоматически: неподдерживаемая версия требует совместимого анализатора или явного пересоздания после ревью.
